# 执行记录：什么算一个节点

> TL;DR：一件事「明天你想不起来、换个人接手看不出」就记一条；一次状态/结论变化对应一条，不对应一次工具调用。`--note` 一句 60 字内，必须含具体对象。
>
> 本节全部是 **agent 口径**：脚本只拒空值、折叠空白，**不校验长度、不校验内容** —— 别指望它帮你把关。

## 判据

**明天你自己想不起来、或换个人接手会看不出** —— 就是一个节点，记一条。
一条 `log` 对应**一次状态变化或一次结论变化**，不对应一次工具调用。

## 该记

| 触发 | `--note` 写成什么 |
|---|---|
| 用户提了新要求 / 改了目标 | 新要求是什么，覆盖了哪条旧做法 |
| 方案变更 / 方案被排除 | 新方案（或排除了哪个）+ 为什么 |
| 改完一批文件 | 动了哪几个模块、验证没有 |
| 跑完验证（**通过或失败都算**） | 跑了什么、结果、下一步是否因此变 |
| 被卡住 / 停下 / 等外部 | 卡在哪一环、缺什么、等谁 |
| 拿到关键外部事实（版本 / 接口形状 / 已核实结论） | 结论 + 来源标识，免得下次重新查 |
| 交付（待验收） | 交付了什么、验收该看哪 |
| 释放 / 重新认领 | 脚本已自动记，别重复记 |

## 不该记

读文件、查命令、跑 `list`、想了一下；纯格式化 / 改错别字 / 依赖锁文件自动变更 —— 这些留在会话或 git 里。

## 写法

- 一句一条，`--note` 会被压成单行；**第一句说明白做了什么**，约 60 字以内，细节写正文对应小节。
- 一轮做了明显不相关的两件事 → 记两条，别拼成一条。
- 自检：一条记录至少能回答「动了什么」—— 含命令 / `文件:行号` / 符号名 / 结论之一。

正例：

```
--note "改了认领即 doing（claim.py:56）"
--note "验证通过：verify 25 项；下一步补 UI 的 overdue 标记"
--note "卡在远端鉴权，缺 deploy key，等用户给"
```

反例：

```
--note "继续推进"                      # 零信息量
--note "我改了代码，应该没问题了"        # 无具体对象 + 替用户下结论
--note "改了 a.ts，又跑了测试，还回了消息" # 三件事挤一条
```
