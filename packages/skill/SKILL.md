# task-ledger

管一个工作区的任务进度：**谁在做、做到哪、什么时候建 / 结**。

- **数据落点与多人并行**：每个工作区下有一个 `ledger/` 目录，任务与进度以静态文件形式存放在里面。**多人协同必须有 git**（认领 / 释放靠推送同步）；没有 git 只写本地，也能用。多人共用却没有 git，提醒用户。
- **任务状态**：`待认领（open）` = 建了还没人认领；`进行中（doing）` = 已认领、在做；`已结案` = 用户明确说结束后由 `close` 产生，此后只读。
- **操作方式**：台账的状态与归属只经命令改；唯一能手写的是过程文档前五节（见「手写边界」）。台账只记「建 / 做 / 结」和指向成果的链接；产出物本身按项目自己的约定落盘。

## 手写边界

- **唯一能手写的是任务的过程文档（worklog）前五节**（怎么写见「过程文档」节）；末节「执行记录」由脚本维护，**禁止手写、禁止手工添加**。
- **其他所有文件一律不许手改**：修改 / 删除 / 任何操作都走命令；手改台账文件即数据损坏。

## 命令参考

十个子命令，前五个是写命令（`new`/`claim`/`set`/`log`/`close`），后五个是只读查询；何时用哪个见「任务生命周期」。参数语法一律看 `<子命令> --help`；下表只说每个参数干什么、何时用。

### new — 建任务

| 参数 | 含义 |
|---|---|
| `--title "…"` | 任务标题（必填）—— 写任务核心、一句话说清干啥；它用来生成任务号和过程文件名，建议 4~20 字 |
| `--id` | 自定义任务号（一般不传：前缀「年月日-时分」与后缀随机码都由脚本按标题自动补；只能用小写字母、数字、汉字和连字符） |
| `--created` | 给过去漏记的任务补建时，补录实际创建日期（`YYYY-MM-DD`；平时不传 = 按现在） |
| `--self` | 建并认领：直接归自己名下、状态「进行中」。仅当用户明确说「并开始做 / 并执行」时才用（判定见生命周期第 2 条） |
| `--category` / `--tags` | 分类 / 标签，口径见本节末尾 |

干什么：建任务、按模板建好过程文档。不加 `--self` = 只建，落公共池等认领；加 `--self` = 建并认领。

分类 / 标签口径（`new` 与 `close` 共用这组参数）：`--category` 答「是什么类型」，单值，中文 ≤4 字 / 纯英文 ≤3 词，吃不准写「其他」；`--tags` 答「涉及什么」，0~5 个、逗号分隔，写不出就不传（传空串等于没传）。tags 不许写 category 的同义词；统计只认 category（精确匹配），查询用 tags（包含匹配）。名词性短语、中文优先。正例：`--category 缺陷修复 --tags "镜像拉取,超时重试"`；反例：`--category 已完成登录修复`、`--tags 修 bug`。

举例：用户说「新建个任务：把发布流程走通」→ `new --title "把发布流程走通"`（只建，不认领）；用户明确说「新建个任务并开始做」→ `new --title "把发布流程走通" --self`。

### claim — 认领

| 参数 | 含义 |
|---|---|
| `--id <任务号>` | 认领哪个（必填） |

干什么：把公共池里的任务认领到自己名下，任务状态变为「进行中（doing）」—— 状态由命令自己改，不用传。已经在别人名下的会拒绝；已在自己名下的会提示无需重复。

举例：用户说「这活我领了」→ `claim --id 20261023-1117-把发布流程走通-7f3a`。

### set — 释放任务（退回公共池）

| 参数 | 含义 |
|---|---|
| `--id <任务号>` | 释放哪个（必填） |
| `--owner ""` | 固定传空串 —— 释放 |
| `--owner <别人>` | 把任务转交给对方（预留通道，**agent 不用**，见纪律） |

干什么：把任务放回公共池、状态回「待认领」，别人即可认领。任务状态只随命令语义变（认领 → 进行中、释放 → 待认领、结案 → 历史），没有单独的「改状态」入口。

举例：用户明确说「把这个任务退回去」→ `set --id <任务号> --owner ""`。

### log — 记一条进展

| 参数 | 含义 |
|---|---|
| `--id <任务号>` | 哪条任务（必填）—— 只能给自己名下的任务记，不在名下会直接被拒 |
| `--note "…"` | 这条记录说什么（必填；一句话，含命令 / `文件:行号` / 符号名 / 结论之一） |

干什么：刷任务的最后进度时间 + 在过程文档「执行记录」节追加一行。改正文必配一条 log（见纪律）；过程文档找不到时只提示、不失败（规则见「过程文档」节）。

举例：一轮干完 → `log --id <任务号> --note "改了认领即 doing（claim.py:56）；下一步同步文档"`。

### close — 结案

| 参数 | 含义 |
|---|---|
| `--id <任务号>` | 结哪条（必填） |
| `--summary "…"` | 结案摘要（必填；放弃写「放弃：原因」） |
| `--finished` | 给漏记的旧任务补用时，补录实际结案时间（`YYYY-MM-DD[ HH:MM[:SS]]`；平时不传 = 按现在） |
| `--category` / `--tags` | 覆盖分类 / 标签终值（写进历史行） |

干什么：结案并封卷过程文档、移出自己名下。**封卷后只读**（见生命周期第 8 条）。

举例：用户明确说「把这个任务结束掉」→ `close --id <任务号> --summary "发布流程走通，验证 25 项全过"`。

### list — 查在办

| 参数 | 含义 |
|---|---|
| `--mine` | 只看自己名下的 |
| `--pool` | 只看公共池（没人认领的） |
| `--owner <邮箱>` | 看某个人的（精确匹配；邮箱在 `list --json` 里那个人名下的任务上能看到；没有 `me` 缩写） |
| `--status open\|doing` | 按状态筛（逗号分隔可多选；合法值只有 `open` / `doing`） |
| `--category` / `--tag` | 按分类（精确）/ 标签（包含）筛 |
| `--since` / `--until` | 按创建时间筛（只给日期含当天） |
| `--json` | 输出 JSON（`{任务号: 任务对象}`） |

干什么：合并公共池 + 各人名下的任务，列出在办。**默认就是全量**，没有 `--all` 参数；收窄用 `--mine` / `--pool`。

举例：「现在该做什么」→ `list --mine`；「有哪些没人认领的」→ `list --pool`。

### show — 看一条任务

| 参数 | 含义 |
|---|---|
| `--id <任务号>` | 看哪条（必填；谁名下的都能看） |
| `--json` | 连过程文档全文一起给（人话模式只给路径） |

干什么：拿任务 JSON + 过程文档路径 / 全文。改既有任务正文前，先用它拿路径。

举例：「这个任务到哪一步了」→ `show --id <任务号> --json`。

### history — 查已结案

| 参数 | 含义 |
|---|---|
| `--owner <邮箱>` / `--mine` | 按 owner 筛 |
| `--category` / `--tag` | 按分类 / 标签筛 |
| `--since` / `--until` | 按创建时间筛 |
| `--months N` / `--limit N` | 最近 N 个自然月 / 最近 N 条 |
| `--count-only` | 只输出 `{"count","capped"}`（与 `--json` 互斥） |
| `--json` | JSON 输出 |

干什么：查历史层。人话一行一条：结案时间、负责人、标题；要摘要 / 分类 / 标签 / 完整时间用 `--json`。

举例：「上周做过什么」→ `history --since <上周一日期>`。

### tags — 标签统计 / 归并

| 参数 | 含义 |
|---|---|
| `--all` | 统计过程文档的分类 / 标签 / 按人（创建人）/ 按月频次（只读） |
| `--rename 旧 新` | 把自己名下在办任务里的旧标签归并成新值 |
| `--dry-run` | 预览：报条数与任务号，零写盘 |

干什么：标签的统计与归并。典型场景：标签写漂了 —— 同一个意思，有的任务写「bug 修复」、有的写「缺陷修复」，用 `--rename` 统一。注意归并**只改自己名下**的在办任务（公共池里的不动，已封卷的不动），且旧值同时命中分类和标签时只改分类。必须带 `--all` 或 `--rename`，裸跑会报错退出。

举例：「标签太乱」→ `tags --all` 看频次；用户点名「这两个标签一个意思」→ `tags --rename 旧 新 --dry-run` 报条数与任务号，用户确认后去掉 `--dry-run`。

### validate — 台账体检

| 参数 | 含义 |
|---|---|
| `--json` | JSON 输出 |

干什么：只读检查结构问题（索引与数据不一致、公共池里混了已认领的任务等）。查出问题会退出码 1 并给清单 —— 只报不改、不自动修；另有只提示不判错的情况。

举例：台账可疑 → `validate`。

## 怎么调用

```bash
python3 <本 SKILL.md 所在目录>/scripts/progress.py <子命令> --repo <当前工作区>
```

- 定位项目：`--repo <目录>` 给了就用；不给就从当前目录逐级向上找第一个含 `ledger/` 的目录，找不到直接报错。
- `--no-sync`（放在子命令**前**）：用户明确要求「先别同步」时才用；之后自己 `git add ledger && commit && push`。
- `--json` 只对只读命令（`list` / `show` / `history` / `validate` / `tags --all`）有意义；写命令不接收 `--json`，传了是用法错。`--json` 里的时间字段是 UTC，人话输出是本地时间。
- 命令回执只用来确认生效；任务状态以 `show` / `list` 为准。

## 任务生命周期

用户要「做某件事」时按这条线走。

1. **建（只建，不认领）—— 默认**：「新建一个任务」「新建个任务，我们来干 X」「新建个任务，我需要处理 Y」→ `new --title "…"`。落公共池、待认领。
2. **建并认领 —— 仅限明确说法**：用户明确说「新建一个任务**并开始做 / 并执行**」这类带着「现在就开始」的话 → `new --title "…" --self`。直接归自己名下、「进行中」。**除这种明确说法，其他一律按第 1 条只建** —— 别替用户决定他要开始做；拿不定，问一句。
3. **找已有的**：用户说「我们来做 X」→ 先 `list --mine` 找自己名下的，在做的直接接着做；没有 → `list --pool` 里找，找到先问用户：「X 还没认领，认领它吗？」→ 用户点头再 `claim`；哪儿都没有 → 按第 1/2 条的判定规则建。
4. **认领**：`claim --id <任务号>` —— 认到自己名下，状态即「进行中」。
5. **推进**：改 worklog 前五节 → 按「过程文档」节的收工三步记 `log`。卡住也 `log`（写清卡在哪，状态不动）；「先放一放」同理 —— 是暂停，不是释放。
6. **交付待验收**：任务留「进行中」，「待办」写「待用户验收」，「下一步」写清验收看什么；照收工三步记一条 `log --note "已交付待验收：…"`。
7. **释放**：仅当用户明确说「退回去 / 释放掉」→ `set --id <任务号> --owner ""`。任务回公共池，别人可认领。
8. **结案**：仅当用户明确说「把这个任务结束掉 / close 掉」→ `close --id <任务号> --summary "…"`；说得含糊（「做完了」「验收通过」）先反问「是要结束这个任务吗？」。收尾顺序：**先补完正文 + 记 log，最后才 close** —— 关了就不能再写。
9. **查询**：在办 `list` / 单条 `show` / 已结案 `history` / 标签 `tags --all` / 体检 `validate`。

## 过程文档

`new` 按模板建好六节骨架，路径由 `show` 给出；前五节是本 skill 唯一允许手写的内容。

| 节 | 写什么 |
|---|---|
| 背景 | 为什么做：触发它的原话 / 现象 / 链接 |
| 待办 | 还没做的、没验证的、等别人给东西的 |
| 下一步 | 下一个**具体动作**（文件:行号 级别），不写「继续推进」 |
| 过程 | 踩坑与证据：带 revision + `文件:行号` 或符号名 |
| 结论 | 做成了什么、留了什么坑；只写可验证事实，评价等用户验收 |
| 执行记录 | 脚本维护，**禁止手写**（见「手写边界」） |

规则：

- 「执行记录」节名一个字都别动；老文档缺这一节也不用补 —— 脚本首次记 log 时自会在文末补上。
- 过程文档找不到时 `log` 只提示不失败；用 `show` 查路径，不要手写。
- 头部只有创建时间 / 创建人、封卷标记、分类 / 标签行 —— **状态与归属以台账数据为准，别从头部读**。
- 执行记录行格式 `- 本地时间 · 类型 · @谁 · 说明`，`@谁` 是这次动手的人、不是任务现归属；只追加、不改旧行。行首「类型」是脚本内部动作名（会见到 `release`，它就是 `set --owner ""`）；认不出就别当成新命令，按 `--help` 查。
- 只改某条任务的正文：`show --id <任务号>` 拿路径直接改，不另建 md；已结案的用 `history` 找回链接，只读不改。

### 收工三步（「收工」= 这一轮对用户有可见产出）

1. 改正文：这轮变化的事实都落笔，「下一步」写具体动作。
2. 跑 `log`：这一轮只要改过正文就必须记（一轮至少一条；纪律见下文）。正文没变也能记一条推进，但要同时重写「下一步」。
3. 回读末行（`tail -n 3 <路径>`）：说明 = 这轮的事。执行记录行的时间是本机本地时间，别以为没记上。

**什么算一个节点**：明天自己想不起来、或换个人接手会看不出的事，就记一条；一次状态 / 结论变化对应一条，不对应一次工具调用。拿不准够不够格、`--note` 不会写 → 见 `references/log-note.md`。

## 纪律

### 数据完整性（脚本管不了的，违反了数据就脏）

- **执行记录禁手改**：只由脚本按 `new / claim / set / release / log / close` 追加，只增不改。
- **改正文必配一条日志**：动了 worklog 的正文（改一句、补一节、改标题、修错字都算）就必须立刻跑一次 `log`。脚本不校验，别指望它兜底。
- **换人只能「释放 → 认领」**：`set --owner ""` 放回公共池，对方自己 `claim`；不许替别人挂名字。`set --owner <别人>` 能把任务直接挂到别人名下 —— 预留转接通道，agent 一律不用。
- **身份由脚本自取，agent 全程不传 owner**：查自己用 `--mine`，只有查别人才传对方邮箱（`list --owner <邮箱>`）；释放传的是空串 `--owner ""`，不是身份。看到「读不到 git 身份」提示 ⇒ 让用户配 git，否则任务记到兜底身份名下。

### 人类授权（跑之前问不问）

项目没有台账目录 ⇒ 先问「要不要建个台账记这活？」，不许自建；用户同意 ⇒ 直接跑第一条写命令（台账目录由脚本自建，没有单独的初始化命令），这之前只读命令只会提示还没有台账。

| 命令 | 档位 | 要求 |
|---|---|---|
| `new` / `claim` / `set` | 动手类 | 执行前把完整参数复述给用户并取得确认 |
| `log` | 免确认 | 本任务的推进 / 卡点 / 交付记录直接跑，跑完一句话交代「已记执行记录：…」；要替用户下结论，先问（任务不在自己名下会直接被拒） |
| `close` | 独立授权 | 仅认明确说「结束掉 / close 掉」（完整判定见生命周期第 8 条）；说得含糊必须反问「是要结束这个任务吗？」；**agent 自判「干完了」不算** |
| `tags --rename` | 一次改多条在办任务 | 先 `--dry-run` 报条数与任务号，用户确认后才去掉 `--dry-run` 真改 |
| `list` / `show` / `history` / `validate` / `tags --all` | 只读 | 直接跑 |

### 故障处置（跑之后出事怎么办）

- **动作阶段失败（输出以 `错误：` 开头）= 该命令没生效**：不挡主任务 —— 继续手里的活，收尾时汇报「没记上，原因 …」；不绕过脚本手改文件。
- **退出码 0 也要看输出**：出现 `提示：` / `错误：` / `警告：` 就先用一句话说清「发生了什么 + 下一步做什么」，再按 `references/troubleshooting.md` 给步骤；纯告知类一句话带过。只读命令只有 `错误：` 才需要转述。
- **两类不是故障的退出码**：`validate` 查出问题时退出码 1，照实转述清单；提交阶段失败 ⇒ 文件已经写下去、只差进 git，让用户先提交再重跑，别说「没记上」。
- **并发冲突**（文件被改动、抢不到锁）重跑一次即可；台账同步一律交给脚本，不要自己 `git pull` / `rebase` 去「解决」。
- 同一仓库里写命令排队执行，等前一个跑完再重跑。
