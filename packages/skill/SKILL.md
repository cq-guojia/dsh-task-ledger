# task-ledger

## 它管什么

| 文件 | 装什么 | 谁写 |
|---|---|---|
| `ledger/progress.json` | 在办任务的状态：任务号 / 标题 / 创建人 / owner / 状态 / 时间 / **分类（`category`）与标签（`tags`）** / 过程文档路径（`worklog` 字段） | **只由脚本写** |
| `ledger/worklog/<年月>/<日>-<时分>-<说明>-<随机码>.md` | 该任务的过程正文，固定五节：背景 / 待办 / 下一步 / 过程 / 结论 | **建档只由脚本按模板做**，之后正文由 agent 直接编辑 |
| `ledger/history/<年月>.md` | 已结案任务，一行一条（8 列：结案时间 / 创建时间 / 工作包 / 分类 / 标签 / **owner** / 摘要 / 过程文档）；按**结案时间**分月。存量 `ledger/PROGRESS-HISTORY.md` 只读兼容、永不重写 | **只由脚本写**；查询走 `history` 子命令 |

这三个文件之外不要另建副本。**不要直接编辑状态表和历史索引 —— 一律走脚本。**
过程文档的**建档也一律走脚本**（`new`）：脚本按模板生成五节骨架、把路径写进状态表；
你只负责往里填正文，**不要自己拼文件名、也不要另建一个 md 顶替它**。

**台账 ≠ 产出物**：台账（`ledger/`）只装「什么时候建 / 谁在做 / 做到哪 / 什么时候结案」
以及**指向成果的链接**；真正的成果（代码、方案、清单、报告）按**所在项目自己的约定**落盘，
**不进 `ledger/`**。两条链不交叉 —— 成果是给人用的，台账是给「未来的自己」查的。

## 什么时候用

✅ 该用：

- 「现在该做什么」「我还有什么没做完」「谁在做这个」
- 「新建一个任务」「我要做 X」
- 「这活我领了」「这个我来做」
- 「卡住了」「先放一放」「转给某人来做」
- 「这活做完了」「结案」
- 「某件老活是什么时候做的」
- 「谁改过什么」「拉某人的工作日志」
- 在已有 `ledger/progress.json` 的项目里开工之前，先查一眼在办任务

❌ 不该用：

- 项目没有 `ledger/` 且只是临时一次性的事 → **不要自动 init**，先问用户
- 只想改某个任务的过程正文 → 那是编辑 Markdown：`show` 会把该文档**全文和路径一起**给你，直接在它上面改（文档已由脚本建好，不要另建一个）。**已结案**任务的过程文档别用 `show` 找（它可能已不在状态表）—— 用 `history` 拿到文档链接再读

## 先判断意图，再选命令

| 用户说什么 | 意图 | 动作 |
|---|---|---|
| 「现在该做什么」「我还有啥没做完」 | 查自己的在办 | `list --mine` |
| 「谁在做 X」「有哪些在办任务」 | 查全部在办 | `list` |
| 「有没有卡住的」 | 按状态查 | `list --status blocked` |
| 「某件老活是什么时候做的」 | 查已结案 | `history`（只读，可直接跑） |
| 「谁改过什么」「拉某人的工作日志」 | 按人查已结案 | `history --owner "<名字>"`（**精确匹配**） |
| 「这周 / 这个月建了啥活」 | 按创建时间查已结案 | `history --since 2026-10-01` |
| 「新建一个任务」「我要做 X」 | 建任务 | `new` |
| 「这活我领了」「我来做这个」 | 认领 | `claim` |
| 「卡住了」「先放一放」 | 改状态 | `set --status blocked` |
| 「继续做」「解卡了」 | 改状态 | `set --status doing` |
| 「转给某人」「交接给某人」 | 换负责人 | `set --owner "<新负责人>"` |
| 「这活做完了」「验收通过」「结案」 | 结案归档 | `close`（**这句必须由用户说**） |
| 项目里还没有状态表 | 初始化 | `init` |
| 状态表看着不对劲 | 体检 | `validate` |

## 命令怎么调

```bash
python3 <本 SKILL.md 所在目录>/scripts/progress.py <子命令> --repo <当前工作区> [参数]
```

> 下表所有命令都省略了 `--repo`，**实际调用时必须带上当前工作区**。

- **脚本位置**：用「本 SKILL.md 所在目录」拼出 `scripts/progress.py` 的路径。**不要依赖任何框架注入的变量**（`{baseDir}` / `$SKILL_DIR` 这类各家 harness 各不相同、未必存在）；若执行环境就在本 skill 目录内，可直接用 `scripts/progress.py`
- **`--repo` 传当前工作区（项目根）**：脚本只知道自己在哪，不可能知道你在哪个项目里干活，这一步必须由调用方给出
- 参数细节用 `<子命令> --help` 查

| 子命令 | 作用 | 关键参数 |
|---|---|---|
| `init` | 建 `ledger/progress.json` | — |
| `new` | 新建任务，并自动建过程文档 | `--title`（必填）、`--id`（可选）、`--self`、`--created`（可选，补录创建时间）、`--category` / `--tags`（可选，分类 / 标签，见下节口径） |
| `claim` | 认领一个待认领任务 | `--id`（必填） |
| `set` | 改状态 / 换负责人 | `--id`（必填）、`--status`、`--owner` |
| `close` | 结案：移出状态 + 追加历史 + 封卷过程文档 | `--id`、`--summary`（都必填）、`--finished`（可选，结案时间）、`--category` / `--tags`（可选，结案时覆盖修正一次） |
| `list` | 查询在办任务 | `--mine`、`--owner`、`--status`、`--since`、`--until`、`--category`（精确）、`--tag`（包含）、`--json` |
| `history` | 查已结案任务（只读） | `--owner`、`--mine`、`--since`、`--until`、`--limit`、`--category`（精确）、`--tag`（包含）、`--json` |
| `show` | 单任务详情 | `--id`（必填） |
| `tags` | 分类/标签巡检与归并 | `--all`（全量频次表）、`--rename 旧 新`（归并在办任务的同值） |
| `validate` | 校验状态表与过程文档是否一致 | — |

### 命令返回什么

| 命令 | 返回 |
|---|---|
| `new` / `claim` / `set` / `show` | 状态行 + **该任务过程文档的路径与全文** —— 拿到就能直接编辑，不用再去找文件、拼路径（`history` 是例外：只给链接不给全文） |
| `close` | 结案结果与摘要 |
| `list` | 在办任务列表（**不含**文档正文，避免撑爆上下文） |
| `history` | 已结案紧凑列表（结案时间 / 创建时间 / owner / 工作包 / 过程文档链接，行尾附所在历史文件），**默认不含摘要**；要摘要走 `--json` |

### 几个必须知道的点

- **状态取值**：`open`（已建待认领）/ `doing` / `blocked` / `done`。**`done` 只能由 `close` 产生**，不要用 `set --status done`。
- **`new --self`** = 建完即认领（直接 `doing`）；**不带 `--self`** = 空开，等别人 `claim`。
- **任务号自动生成**：创建时间（`年月日-时分`）+ 标题里的字母、数字、汉字 + 4 位随机码（如 `20261015-1430-登录接入-sso-7f3a`）。想指定就传 `--id`。
- **owner 取 `git config user.name`**：认领人**只能是当前 git 身份，不能由外部传入**；读不到就直接报错退出（提示「需要用户名才能执行」），不做任何兜底 —— 先让用户配好 git 身份。（`history` 只有 `--mine` 会取这个身份；`--owner <别人>` 是只读查询，不校验身份）
- **只能动自己名下的任务**：`set` 与 `close` 同样先取身份，再校验 `owner` 是不是你。**不是你的直接拒绝**；任务还是 `open`（没人认领）时也拒绝，提示先 `claim`。别人要动你的任务，必须你先交接（`set --owner`）。**`history` 是只读查询，不在此列** —— 查别人的已结案不需要对方交接。

## 时间

- **精度**：任务号、worklog 目录与文件名只到**分**（`年月日-时分`）；其余所有记录时间都到**秒**（`YYYY-MM-DD HH:MM:SS`）。
- **谁来给**：默认不传 —— 脚本取当前时刻（`new` 创建、`claim` / `set` 开始、`close` 结案）。**只在「要记的时间不是现在」时才传**：
  - `close --finished`：用户明说这活是什么时候完成的（不传＝当前时刻）。
  - `new --created`：补录一个过去的创建时间（不传＝当前时刻）。
- **怎么写**：格式随意、只要对 —— `2026-10-06`、`2026-10-06 14:30`、`2026-10-06 14:30:05` 都行，脚本补全到秒（没传秒补 `:00`，没传分秒补 `00:00`）；传了但不对（如 `2026-13-40`）会被拒。
- **结案时间必须存在**：`close` 一定写（不传＝当前）。
- **按时间筛**：`list` / `history` 都有 `--since`（起）/ `--until`（止），都按**创建时间**，可只给其一；只给日期时，起＝当天 `00:00:00`、止＝当天 `23:59:59`（含整天）。`history` 输出里**第一列是结案时间、第二列才是创建时间**，排序也按创建时间。

## 过程文档的生命周期

1. **建档** —— 执行 `new` 时，脚本**必须**按 `assets/worklog.md` 模板创建 `ledger/worklog/<年月>/<日>-<时分>-<说明>-<随机码>.md`（`<年月>` 取任务创建月份，如 `202610`；年月已经在目录名里，文件名不再重复）。路径同时写进状态表的 `worklog` 字段，查的时候不必靠推算。
2. **推进** —— 这个 md 由 **agent 直接编辑**（它是正文，不是状态数据，不走脚本）。五节（背景 / 待办 / 下一步 / 过程 / 结论）**标题结构不能动**。**各写什么、写成什么样算对，模板注释里给了正例**，照它填即可。
3. **交付（待验收）** —— 活干完了但**用户还没验收**时，任务仍留在 `doing`：worklog 的「待办」写「待用户验收」，「下一步」写清验收该看什么（哪条命令、哪个文件）。**这一段不产出状态变化，只写正文。**
4. **封卷** —— 执行 `close` 时，脚本自动打封卷标记并把头部状态改为完成，此后不再修改。历史行按**结案时间**落 `ledger/history/<年月>.md`（存量 `ledger/PROGRESS-HISTORY.md` 只读、不再写入）；封卷后要找回这篇文档：`history` 会给出它的链接与所在历史文件（只读、无需确认）。

## 分类与标签（Agent 自行总结，不设枚举）

**为什么不设枚举**：本 skill 跨所有工作区（开发 / 运维 / 个人事务 / 调研备忘），任何固定分类都覆盖不全、颗粒度难定。所以分类与标签都由 Agent 在 `new` 建档时按本节口径**自行总结**，脚本只硬校验形态（≤4 字 / 纯英文 ≤3 词 / ≤5 个），不校验语义。

| 层 | 答什么 | 约束 | 用途 |
|---|---|---|---|
| `--category`（单值） | 这事**是什么类型**（缺陷修复 / 调研 / 建设 / 运维 / 事务 / 其他） | 只有一个；吃不准就写「其他」 | 人眼扫视 + 看板统计（一条一值，`count by` 干净） |
| `--tags`（1~5 个） | 这事**涉及什么**（对象 / 领域 / 模块，如 `镜像拉取`、`Hindsight`） | 至多 5 个；宁缺毋滥，**不凑数** | 下钻查询（包含匹配，容忍变体） |

三条边界（用户确认，勿破）：

1. **口径错开**：tags 不许写 category 的同义词 —— category=缺陷修复 时，tags 别再写「bug修复」
2. **数量软约束**：3~5 个是目标不是硬指标 —— 设下限会逼出凑数标签，凑的正是噪声；脚本只卡上限
3. **统计与查询分工**：统计只认 category（精确匹配，同值才能比较）；tags 只做查询（包含匹配，「bug」命中「bug修复」正是要的效果）

写法口径（归一化，跨工作区才稳）：

- 名词性短语，不带时态、不用动词收尾：写「缺陷修复」，不写「修复了」「修 bug」
- 中文优先，不中英混排；纯英文 ≤3 个单词（`fix a bug` 可以，`fix a login bug` 超了）
- 标签之间用**逗号**分隔 —— 空格是英文多词标签自身的，不当分隔符（`--tags "fix a bug,docker"`）
- 正例：`--category 缺陷修复 --tags "镜像拉取,超时重试"`；反例：`--category 已完成登录修复`、`--tags 修 bug`

时机与修正：`new` 建档时一并总结（标题 + 背景语义最全）；`close` 可用 `--category` / `--tags` 覆盖修正一次；日常漂移用 `tags --rename 旧 新` 归并（只改在办任务，已封卷文档不动）。看板侧先跑 `tags --all` 看全量频次与低频变体，再决定查什么、归并什么。已结案记录的分类/标签落在 history 行的「分类/标签」列（8 列结构，close 时从 task 终值写入）。

## 写操作红线

`init` / `new` / `claim` / `set` / `close` 都有副作用，但**分两档**：

**一、动手类（`init` / `new` / `claim` / `set`）**：执行前先把完整参数复述给用户并取得确认（任务号、标题、负责人、目标状态）。不得先执行再补报告，也不得一次执行多条用户没逐条确认的写操作。

**二、`close` 是独立授权，不是做任务流程的最后一步**：

- 只能由用户**明确的验收 / 结案指令**触发（「验收通过」「这活结了吧」）。
- **agent 自己判断「我干完了」不算触发条件** —— 那是交付，不是结案。交付后停在 `doing`，把做了什么、`--summary` 打算怎么写交给用户，**等用户回话**（这段时间 worklog 怎么记见下节）。
- 用户没点头就不许先斩后奏，也不许替用户下验收结论。**宁可任务停在 `doing`，也不要悄悄进历史。**

`list` / `show` / `validate` / `history` 是只读，可以直接跑。

## 失败处理

脚本失败时以非 0 退出码 + stderr 说明原因：

| 退出码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 业务错误（参数值 / 状态 / 权限不对，可纠正） |
| 2 | 命令行参数错误 |
| 3 | 未预期的内部失败（应上报，不要重试） |
| 130 | 被中断 |

**报错就停下并原样报告，不要绕过脚本直接改 `ledger/progress.json` 或历史层（`ledger/history/<年月>.md`）。**

并发冲突（文件在操作期间被改动）会报错并中止 —— 重新执行一次即可，**不要用 `git pull` / `rebase` 去「解决」**。
