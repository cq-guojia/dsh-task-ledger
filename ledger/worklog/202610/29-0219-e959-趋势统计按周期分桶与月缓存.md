## 背景

首页右侧趋势图（8 周 × 3 柱）2026-10-28 收敛时被删，只留卡位；当时的结论是「skill 还没有按周汇总的方法」。
本次讨论（2026-10-29）要把趋势数据链重新接上，并解决两个老问题：

- 现有 `history` 的 `--since/--until` 过滤的是**结案时间**，`list` 只有当前在办 ⇒ 用现有方法**取不到「某周新增」**，
  多次调 `--count-only` 也拼不出来（不是慢，是口径缺一块）。
- `history --json` 搬全量明细再在插件侧聚合已被实测否决（20 万条 3s+、30MB 过进程边界），
  文档 `host-data-plane.md:110` 早有一条挂起项「脚本聚合模式：history 直接按周回分组计数」。

用户决定：在 skill 里加一个按周期统计的方法，并把已过去月份的统计结果落成缓存文件。

原设计（`docs/design/features/board-home.md:68-69`）：每周三根柱「完成 / 未结 / 新增」，
未结 = 该周截止时仍未结案；口径要求天然含窗口前遗留基线，不需要快照库。

## 决议（本轮全部拍板项）

**A. 方法形态**

- A1. skill 新增子命令
  `stats --trend <day|week|month|quarter|year> [--since <起> --until <止> | --last <N><d|w|m|y>] [--mine|--owner <uuid>[,<uuid>...]] [--by-owner]`，
  **在 skill 里算完再回**：一次遍历返回整段桶序列，不按桶多次调用。
- A4. `--since` / `--until` 按**用户本地时区**给（与现有 `--since/--until` 同口径），最后转 UTC 比较。
- A5. 区间与桶不对齐时**按区间裁剪首尾桶**：区间从周三开始，第一桶只有周三起的数据（用户 2026-10-29 明确）。
- A6. `--owner` 支持**多个用户**（逗号分隔 uuid），用于只看某几个人；与 `--mine` 互斥。
- A7. 时间参数二选一：要么 `--since/--until`，要么 `--last 8w / 1m / 1y / 14d`（与前者同给即用法错）；
  **默认 `--last 8w`**。
- A8. 按人明细默认**不返回**（只给总数），要按人看时显式加 `--by-owner`，届时一并回人名（名字实时取自 `owners.json`，不进缓存）。
- A2. 插件侧只做「跨工作区扇出 + 求和 + 降级归集」，不判断任何口径；前端只渲染。
- A3. 趋势单独走 `/board/trend` 按需拉，不进首屏 `/board/snapshot`（趋势是秒级，首屏不能被它拖）。

**B. 数据源与口径**

- B1. 读 `pool.json` + 各人分片（在办：本期新增但还没结的任务只在这里）+ `ledger/history/*.md`（已结案的 created/finished）。
- B2. 历史文件仍受 `MaxHistoryFiles`=13 限制；只读「结案时间落在 [窗口起, now]」的月份文件，不是全量扫。
- B3. 「新增」按 `created`；「完成」按 `finished`（与现有统计卡一致）。
- B4. 桶边界（全部按**本机时区**）：日 = 00:00 起；周 = **周一 00:00 起**；月 = 自然月 1 日起；
  **季 = 自然季度（1~3 / 4~6 / 7~9 / 10~12 月）**；年 = 自然年 1 月 1 日起。周最多跨 2 个自然月。
- B5. 解析出 11 列后直接进桶：不 `ToMap`、不排序、不读名册（沿用 2026-10-29 `--count-only` 快路径的做法）。

**C. 剩余（未结）**

- C1. `剩余(W) = 当前在办总数 + Σ完成(W, now] − Σ新增(W, now]`（倒推，只依赖 W 之后的数据 + 当前在办）。
- C2. 剩余**进缓存**（每月的月末值落盘），不再每次回溯倒推。
- C3. 不做逐月累加链：每月剩余独立存放，一条补录最多造成「该任务活跃区间内每月偏 1」，**不级联、不放大**。
- C4. 补录（`new --created` / `close --finished`）造成的偏差**明确接受，不处理**。

**D. 缓存**

- D1. 粒度：**一月一文件，文件内按天存明细** `{day, added, done, open}`，周期（周/月/年）一律由天拼。
- D2. 每个文件另存 `month_end_open`（该月末在办数）、`week_start`、`algo` 版本、`source` 指纹数组。
- D3. 校验只认**该月自己的源文件指纹**（`size + mtime_ns`），不追后续月份；对不上就重算。
- D4. **当月不缓存**，永远实时算；空月份也写文件（省掉「有没有」的二次判断）。
- D5. `algo` 版本一变，全部缓存视为过期（口径改了不必依赖文件时间）。
- D6. 读路径：先找缓存 → 有就用 → 没有就「读源文件算 + 原子写缓存 + 返回」。
- D7. 生成时机：查询时缺则生成；每次查询顺带补上个月，避免月份老出去之后再无机会生成。
- D8. 原子写（临时文件 + rename），多进程同时写同一个月结果一致。
- D9. 缓存按 `offset` 分目录；offset 不同的机器不复用（+8 的「10 月 1 日」在 +6 里边界差 2 小时）。
- D10. 返回里带 `coverage{from,to}`；窗口超出覆盖范围时前端显示「数据不足」，不画 0、不画假线。
- D11. **跨月源**：本地月可能横跨两个 UTC 月文件（+8 的 1 月初住在 12 月文件、-5 的 1 月末住在 2 月文件）
  ⇒ `source` 必须记**两个**文件的 size+mtime，任一个变了就重算。
- D12. **生成时机按时区**：只有该**本地月**已经过完才固化缓存（当月永远实时算），否则末尾几小时会缺。
- D13. 时区只由目录名决定，JSON 里不再存 tz 做自检（手挪目录是使用者自己的事，不处理）。

**E. 性能与稳定性**

- E1. 多工作区扇出要限并发（2~4），避免 N 个进程同时解析把 CPU 打满；skill 是独立进程，不会卡 Node 主线程。
- E2. 缓存采用「延迟一次生长」：能查多深取决于生成过多少个月，没生成过的老月份补不回来（已接受）。

**F. 按人细分（已定稿，与 H 一起生效）**

- F1. 缓存内再存 `per_owner: {uuid: [ {day, added, done, open} ]}`，供「按人统计」类查询。
- F2. 「某人今天干了什么」需要标题 / 摘要等明细，缓存只存计数 ⇒ 明细仍走 `history --json` / `list`，不塞进缓存。
- F3. 预估体量：100 人 × 30 天 = 3000 条计数/月，JSON 体积可接受。

**G. 缓存落点（本轮拍板）**

- G1. 放 `~/.taskledger/cache/trend/<仓库绝对路径哈希>/<offset>/<YYYYMM>.json`，**本机私有、不进 git**。
- G2. 不共享的理由（已论证）：`mtime` 指纹跨机必然失效（pull / checkout 会改 mtime）；
  缓存自动提交会让「有未推送的台账提交」成为常态，正好撞上写前 guard（有未推送台账提交即中止）；
  JSON 生成物在 git 里没有可移植的「后者覆盖前者」策略（`merge=union` 拼坏 JSON，`merge=ours` 需每机本地配置）。
- G3. 真要跨机共享就不走缓存，改走「每月快照随台账提交」的另一条路（本轮不做）。

**H. 按人计数与「当天在途」（本轮拍板）**

- H1. 「某人今天干了什么」= 当天该人**新增数 + 完成数**，**没有剩余**；明细（标题 / 任务号）仍走 `history --json` / `list`，不进缓存。
- H2. 缓存里 `per_owner` 只存 `{uuid: {day, added, done}}`，只存 uuid 不存名字（改名不该让缓存失效）。
- H3. 「当天结束时在办总数」可精确算（就是剩余口径，见 C1）。
- H4. 「按人当天在途」**只用 `owner` + 是否结案判定，不引入 `started`**（用户 2026-10-29 明确否决加列）：
  某天某人手上 = `owner` 是他的任务中、当天还没 `finished` 的条数。待认领（owner 空）不算任何人；
  认领后长期没更新也算他的；转手按最终 owner 回填（用户明确接受）。`started` / `updated` 都不参与。
- H5. `--count-only` **暂不删除**：trend 上线后首页「本周 / 上周完成」改由 trend 供数，观察一段再决策；
  届时把它降级为同一条日桶路径的薄壳，不保留第二套计数逻辑。
- D13（2026-10-29 追加拍板，推翻本轮实现时的「借 `history` 的 13 文件上限」）：
  - **trend 的上限按时间定，不按读几个文件定**：一次最多 10 年（`TrendMaxDays` 3660 天）；
    `day` 粒度另有 365 天上限（`TrendMaxDayBuckets`）。理由：一年固定 12 个文件，用文件数限制
    等于用「台账有多老」限制「你想看多久」，而真正的成本是数据量、不是文件个数；
    且按文件数限会把 `quarter` / `year` 这两个「看多年」的粒度直接废掉。
  - `history` 的 13 个月**保持不动**：它是产品窗口（插件历史 tab 只看 13 个月），不是读保护，文档不改。
  - **缓存文件不计入任何上限**（命中的月份根本不读源文件）；缓存只决定**多快**，不决定**能查多久** ——
    历史文件从不清理，10 年的库就是 120 个文件在盘上，有没有缓存都能查到 10 年。

## 接口与输出（2026-10-29 定稿）

```json
{
  "granularity": "week",
  "coverage": { "from": "2026-09-01", "to": "2026-10-29" },
  "buckets": [
    {
      "from": "2026-09-01", "to": "2026-09-06",
      "added": 3, "done": 5, "open": 12,
      "owners": { "<uuid>": { "name": "某人", "added": 1, "done": 2, "open": 4 } }
    }
  ],
  "warnings": []
}
```

- `buckets`：一桶一行，`from`/`to` 是**本地日期**（含边界；首尾桶按请求区间裁剪）。
- `coverage`：实际有数据覆盖的区间；请求超出部分前端显示「数据不足」。
- `owners`：**只有加 `--by-owner` 才出现**（默认不返回，只给总数）；`added` 按 `creator`，`done` / `open` 按 `owner`，`name` 实时取自名册（不进缓存）。
- 只出 JSON，不出人话表格（表格由插件渲染）。`--trend` 与 `--json` 不叠加（`--trend` 自带 JSON）。

**I. 标签与展示（本轮拍板）**

- I1. 后端**只回时间区间**（`from` / `to` + `granularity`），**不返回任何展示标签**；标签由前端按粒度生成：
  day `10-01`、week `第 40 周` / `W40`、month `2026-10`、quarter `2026 Q4`、year `2026`。
- I2. 周号用 **ISO 周**（周一起算，与桶边界一致；跨年按 ISO 规则，`2026-12-29` 属 `2027-W01`）。
- I3. 前端**禁止** `new Date("YYYY-MM-DD")` 再取年月（按 UTC 解析，负时区会错一天）：直接切字符串；周号写成纯函数 + 单测（覆盖 12-29 ~ 01-04）。
- I4. 可选（不强制）：返回里带纯 ASCII `key`（`2026-Q4` / `2026-W40` / `2026-10` / `2026-10-01` / `2026`），只用于 React key 与排序，不用于展示。

## 结论

- skill 新增 `stats --trend <day|week|month|quarter|year>`：一次遍历回整段桶序列
  （`added` / `done` / `open`，可选 `owners`），区间用 `--since/--until` 或 `--last <N><d|w|m|y>`（默认 8w），
  可按 `--mine` / `--owner`（多 uuid）收窄；只出 JSON，口径与桶边界见 `packages/skill/SKILL.md` 的 `stats --trend` 小节。
- 已过完的本地月落本机缓存（不进 git、随时可删），当月实时算；缓存只加速，读不出来 / 写不进去都不影响结果。
