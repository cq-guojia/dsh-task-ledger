## 背景

首页右侧趋势图（8 周 × 3 柱）2026-10-28 收敛时被删，只留卡位；当时的结论是「skill 还没有按周汇总的方法」。
本次讨论（2026-10-29）要把趋势数据链重新接上，并解决两个老问题：

- 现有 `history` 的 `--since/--until` 过滤的是**结案时间**，`list` 只有当前在办 ⇒ 用现有方法**取不到「某周新增」**，
  多次调 `--count-only` 也拼不出来（不是慢，是口径缺一块）。
- `history --json` 搬全量明细再在插件侧聚合已被实测否决（20 万条 3s+、30MB 过进程边界），
  文档 `host-data-plane.md:110` 早有一条挂起项「脚本聚合模式：history 直接按周回分组计数」。

用户决定：在 skill 里加一个按周期统计的方法，并把已过去月份的统计结果落成缓存文件。

原设计（`docs/design/features/board-home.md:68-69`）：每周三根柱「完成 / 未结 / 新增」，
未结 = 该周截止时仍未结案；口径要求天然含窗口前遗留基线，不需要快照库。

## 决议（本轮全部拍板项）

**A. 方法形态**

- A1. skill 新增子命令 `stats --trend <day|week|month|year> --since --until [--mine|--owner]`，
  **在 skill 里算完再回**：一次遍历返回整段桶序列，不按桶多次调用。
- A2. 插件侧只做「跨工作区扇出 + 求和 + 降级归集」，不判断任何口径；前端只渲染。
- A3. 趋势单独走 `/board/trend` 按需拉，不进首屏 `/board/snapshot`（趋势是秒级，首屏不能被它拖）。

**B. 数据源与口径**

- B1. 读 `pool.json` + 各人分片（在办：本期新增但还没结的任务只在这里）+ `ledger/history/*.md`（已结案的 created/finished）。
- B2. 历史文件仍受 `MaxHistoryFiles`=13 限制；只读「结案时间落在 [窗口起, now]」的月份文件，不是全量扫。
- B3. 「新增」按 `created`；「完成」按 `finished`（与现有统计卡一致）。
- B4. 桶边界：**本机时区**、**周一 00:00 起**；周最多跨 2 个自然月。
- B5. 解析出 11 列后直接进桶：不 `ToMap`、不排序、不读名册（沿用 2026-10-29 `--count-only` 快路径的做法）。

**C. 剩余（未结）**

- C1. `剩余(W) = 当前在办总数 + Σ完成(W, now] − Σ新增(W, now]`（倒推，只依赖 W 之后的数据 + 当前在办）。
- C2. 剩余**进缓存**（每月的月末值落盘），不再每次回溯倒推。
- C3. 不做逐月累加链：每月剩余独立存放，一条补录最多造成「该任务活跃区间内每月偏 1」，**不级联、不放大**。
- C4. 补录（`new --created` / `close --finished`）造成的偏差**明确接受，不处理**。

**D. 缓存**

- D1. 粒度：**一月一文件，文件内按天存明细** `{day, added, done}`，周期（周/月/年）一律由天拼。
- D2. 每个文件另存 `month_end_open`（该月末在办数）、`tz`、`week_start`、`algo` 版本、`source` 指纹。
- D3. 校验只认**该月自己的源文件指纹**（`size + mtime_ns`），不追后续月份；对不上就重算。
- D4. **当月不缓存**，永远实时算；空月份也写文件（省掉「有没有」的二次判断）。
- D5. `algo` 版本一变，全部缓存视为过期（口径改了不必依赖文件时间）。
- D6. 读路径：先找缓存 → 有就用 → 没有就「读源文件算 + 原子写缓存 + 返回」。
- D7. 生成时机：查询时缺则生成；每次查询顺带补上个月，避免月份老出去之后再无机会生成。
- D8. 原子写（临时文件 + rename），多进程同时写同一个月结果一致。
- D9. 缓存按 `offset`（如 `+08:00`）分目录；offset 不同的机器不复用（+8 的「10 月 1 日」在 +6 里边界差 2 小时）。
- D10. 返回里带 `coverage{from,to}`；窗口超出覆盖范围时前端显示「数据不足」，不画 0、不画假线。

**E. 性能与稳定性**

- E1. 多工作区扇出要限并发（2~4），避免 N 个进程同时解析把 CPU 打满；skill 是独立进程，不会卡 Node 主线程。
- E2. 缓存采用「延迟一次生长」：能查多深取决于生成过多少个月，没生成过的老月份补不回来（已接受）。

**F. 按人细分（讨论中，尚未定稿）**

- F1. 缓存内可再存 `per_owner: {uuid: {day, added, done}}`，供「按人统计」类查询。
- F2. 「某人今天干了什么」需要标题/摘要等明细，缓存只存计数 ⇒ 明细仍走 `history --json` / `list`，不塞进缓存。
- F3. 预估体量：100 人 × 30 天 = 3000 条计数/月，JSON 体积可接受。

**G. 缓存落点（本轮拍板）**

- G1. 放 `~/.taskledger/cache/trend/<仓库绝对路径哈希>/<offset>/<YYYYMM>.json`，**本机私有、不进 git**。
- G2. 不共享的理由（已论证）：`mtime` 指纹跨机必然失效（pull / checkout 会改 mtime）；
  缓存自动提交会让「有未推送的台账提交」成为常态，正好撞上写前 guard（有未推送台账提交即中止）；
  JSON 生成物在 git 里没有可移植的「后者覆盖前者」策略（`merge=union` 拼坏 JSON，`merge=ours` 需每机本地配置）。
- G3. 真要跨机共享就不走缓存，改走「每月快照随台账提交」的另一条路（本轮不做）。

**H. 按人计数与「当天在途」（本轮拍板）**

- H1. 「某人今天干了什么」= 当天该人**新增数 + 完成数**，**没有剩余**；明细（标题 / 任务号）仍走 `history --json` / `list`，不进缓存。
- H2. 缓存里 `per_owner` 只存 `{uuid: {day, added, done}}`，只存 uuid 不存名字（改名不该让缓存失效）。
- H3. 「当天结束时在办总数」可精确算（就是剩余口径，见 C1）。
- H4. 「按人当天在途」**只用 `owner` + 是否结案判定，不引入 `started`**（用户 2026-10-29 明确否决加列）：
  某天某人手上 = `owner` 是他的任务中、当天还没 `finished` 的条数。待认领（owner 空）不算任何人；
  认领后长期没更新也算他的；转手按最终 owner 回填（用户明确接受）。`started` / `updated` 都不参与。
- H5. `--count-only` **暂不删除**：trend 上线后首页「本周 / 上周完成」改由 trend 供数，观察一段再决策；
  届时把它降级为同一条日桶路径的薄壳，不保留第二套计数逻辑。
