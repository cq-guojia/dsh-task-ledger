## Process

### 一、数据面事实（已核实）

- 历史按月一个文件 `ledger/history/<年月>.md`，行按**结案动作顺序追加**，因此文件内天然是结案时间升序；`close --finished` 补录会把老时间的行追加到末尾，破坏该顺序（按用户决定不处理）。
- `history` 没有 offset / 页码，只有 `--limit`（截前 N 条），一次最多读 13 个月文件（`actions/query_history.go:20`），不给时间参数默认近 3 个月（`:22`）。
- 单条记录 JSON 实测 927B（45,445B / 49 条，本仓近 2 个月）。
- skill 支持的过滤只有 `--owner` / `--owner-name` / `--mine` / `--category` / `--tag` / `--since` / `--until` / `--limit` / `--months`；**没有关键字搜索**。

### 二、压测（合成数据，`/tmp/ledger-bench`：6 个月 × 1.67 万行 = 10 万行，每月 10.8MB）

| 场景 | 改前 | 去掉排序后 |
|---|---|---|
| 单月 1.67 万行取 20 条 | 0.63s | 0.67s |
| 半年 10 万行取 20 条 | 2.9s | 2.57s |
| 峰值 RSS（半年区间） | 394MB | 同量级（未早停时仍全量解析） |

结论：耗时在**解析整份文件**（约每 1.67 万行 0.6s），排序只占极小部分；一条记录在 Go 侧约 4KB。

### 四、方案（2026-10-31 评审后定稿，未落码）

**总原则**：核心只接受「时间区间 + 已有过滤参数」，不加游标、不加 offset、不加分页参数。列表与顶部柱状图**互不关联**（用户 2026-10-31 明确：两块独立，下面翻到哪不影响上面）。

**浏览模式（默认）**

1. 先取当月按天统计（`/history/trend?gran=day&since=月初&until=今天`，带 `--by-owner`）——日桶的 `done + cancelled` 就是那天的历史行数；
2. 从最近一天往前累加，凑够 **20 条** ⇒ 得到要取的日期区间 `[最早, 最近]`；
3. 每仓**一次** `history --since 最早 --until 最近 --json`（并行，当天全量，不带 `--limit`）；
4. 显示：一级按天分组（可弱化），二级按工作区分组，组内结案时间倒序；
5. 凑不够 20 条 ⇒ 取上个月统计，重复 2~3；到「一年」或台账起点停，给「已到最早记录」。

- **过滤只有两个，都下推**：工作区（只读该仓，其他仓不启动）、执行人（统计 `--by-owner` + 取数 `--owner <uuid>`）。两侧同一条件 ⇒ 条数一致，不会出现「取回来筛完不够」的循环。
- 渲染：定高虚拟列表（日期组头 32 / 工作区组头 24 / 记录行 64），组头拍平进数组，总高 = 各类项数 × 定高；用户感知与普通长列表一致。
- 底部「加载更早的记录」继续上面的循环；不做页码、不做游标。
- 任一仓读失败 ⇒ **整次报错**（人话带仓名与原因），不做部分展示。

**搜索模式（关键词 / 标签 / 分类）**

- 独立结果页，**不按天分组**，平铺；每行带日期 + 工作区 + 标题 + 标签（不分天就必须自己带归属）。
- 每仓最多 50 条（`--limit 50`），窗口默认 3~6 个月（见 §六），跨仓合并后前端排序。
- 前置依赖：skill 需新增 `--keyword`；标签 / 分类用已有的 `--tag` / `--category`。
- 界面注明「每仓最多 50 条、仅搜索最近 N 个月」。

### 五、被否掉的方案

- **游标分页**（`--before` + 每仓续取）：用户明确否掉，「局限性太大」。
- **offset / 页码**：skill 没有 offset；深翻页每页都要从最新月份重数。
- **全量进内存**：一年 10 仓 × 200 条/天 = 73 万条 ≈ 677MB JSON，V8 解析后 1.5GB+，标签页崩。
- **服务端合并状态**（host 记游标）：跨工作区的东西不在同一处，不考虑。
- **每仓取前 20 条**（k 路归并）：与「一天必须完整」冲突 —— 当天第 21 条以后会被丢掉。
- **列表复用顶部趋势的日桶**：用户否掉，不愿为复用多写一层；列表自己按月请求统计。
- **逐天串行拉**：稀疏台账要 20 轮 × 0.67s ≈ 13s，改为「统计定天数 + 一次区间取回」。
- **读取失败保留空组头**：用户否掉，直接报错。

### 六、资源与耗时核算（评审）

| 项 | 数字 | 依据 |
|---|---|---|
| 首屏 | 统计 0.7s + 取数 0.7s ≈ **1.4s** | 单月文件解析实测 0.67s；月缓存命中后统计降到百毫秒级 |
| 跨月的「加载更早」 | +0.7s（上月统计）+0.7s（取数） | 同上 |
| 同月文件被解析两次 | 统计一次 + 取数一次 | 取数路径没有月份缓存 |
| 当月统计不进月缓存 | 每次都要实时算 | skill 的月度缓存只覆盖已过完的月 |
| 搜索窗口内存 | 3 个月 × 5 仓 ≈ 350MB；13 个月 ≈ 1.5GB | 10 万行 394MB 实测线性外推 |
| 单日全量传输 | 500 条/仓 × 5 = 2500 条 ≈ 2.3MB | 单条 927B |

### 七、可实现性

全部可实现，**不需要新增 skill 方法**（除 `--keyword` 一个参数）：

| 件 | 现状 |
|---|---|
| 按天统计 + 按人日桶 | `stats --trend day --by-owner` 已支持；插件 `readTrendGran` 没传 `--by-owner`，补一个参数 |
| 区间取数 + 按人过滤 | `history --since --until --owner` 已支持 |
| 关键词 | **缺**，需加 `--keyword`（约 15 行 + 测试），并升 skill / plugin 两个 tag |
| 定高虚拟列表 | 新写（约 100 行），无现有实现可复用 |
