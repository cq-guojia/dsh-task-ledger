## 背景

用户原话：「这鸡巴的这个完全用不了啊，太他妈脆弱了」——`progress.json` 单文件 + git 行级合并，删一行（close）和末尾加一行（new）挤在同一片区域就撞，同一任务被两边改更是只能人工合。

用户拍板的规则：**不同任务各自改动要自动合上；同一任务被两边同时改必须报冲突，不许静默选一个**（「早的那次会丢」「你一个 owner 也可能两台机器在改」）。

## 待办

- 待用户验收：两台机器改不同任务应无感合并；改同一任务应停下并标出双方版本。

## 下一步

用户验收该看：① 一机关一个任务、另一机新建任务 → 推送直接成功、无冲突标记；② 两关改同一任务 → 命令中止、`progress.json` 里带 `<<<<<<< 本地 / >>>>>>> 远端` 标记、worklog 两边执行记录都在。

## 过程

**先确认路线。** 实测过 git 的自定义 merge driver：`git merge` 会调用它，**`git rebase` 不会**。脚本的同步走的是 rebase，所以配 driver 没用 —— 改成「rebase 冲突后脚本自己接管」才既保留现有同步路径又拿到语义合并。

**合并单位定成任务，不是文本行。** `_merge_task_dicts`（`packages/skill/scripts/progress.py:554` 起）按 taskId 三方对账：`ours == theirs` 保留、`ours == base` 取远端、`theirs == base` 取本地，三者都不同才进冲突。

**踩坑一：只接管 progress.json 时功能等于没开。** 第一版检查 `conflicted != [rel]`，但两台机器同改一个任务时 **worklog 也会冲突**（各自追加一条执行记录）→ 条件不成立 → 直接退回人工。改成：台账目录下的冲突全接管，progress.json 走语义合并，worklog 走 `git merge-file --union`（追加式正文两边都留），业务代码的冲突一个字不碰。

**踩坑二：测试造不出冲突。** 两次 `log` 落在同一秒，`updated` 字符串完全相同 → 两个版本字节一致 → 判成「没冲突」是对的。用例里加两次 `sleep 1.1` 才真正造出两个不同版本。

**验证。** 场景 A（a 关 T3 / b 建 T4）：提示「合并时按任务号自动对账了台账」，最终 T3 没了 T4 在、无冲突标记、工作区干净、推送成功。场景 B（两火同时 log 同一任务）：命令中止、`progress.json` 标出本地/远端两版、worklog 两边记录都在且无冲突标记。`npm run verify` 32 项通过（新增一条用例）；`koc-codelint` 六层全过（L3 经 `--fix` 后复跑）。

## 结论

- 合并粒度从「文本行」改成「任务」：不同任务的改动自动合上，不再因为删一行 + 加一行挤在文件末尾就撞。
- 同一任务被两边改 → 中止命令，`progress.json` 里逐任务标出 `<<<<<<< 本地 / >>>>>>> 远端`，worklog 用 union 合并保住两边记录，不静默选任何一边。
- 不需要 `.gitattributes`、不需要 `git config`：全靠脚本在 rebase 冲突时接管，零配置。
- 边界：业务代码的冲突仍走原路径（abort + 提示手动处理），脚本只碰 `ledger/` 下的数据。
- 补记（2026-10-21）：本任务在「单文件 + 行级合并」前提下把合并做到极限；根因是容器形态而非合并算法，已有新方向接手，本任务就此封卷，不再在本文推进。
