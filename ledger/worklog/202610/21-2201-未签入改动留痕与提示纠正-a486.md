## 背景

另一 Agent 汇报的三个「已写未提交」盲区，核实后两个成立：

1. **`--no-sync` 完全静默**：`git_sync` / `git_presync` 开头一句 `return` 就结束，一个字都不打。其他失败路径都有 stderr，唯独这条没有 → 写成功了却没人知道没签上。
2. **守卫的报错说不清真因**：下次写命令撞上「本地台账有未提交改动，写前取最新会覆盖它」，原因写的是「将被覆盖」，而真因是「上次没签回来」。处理步骤给了，但用户猜不到是怎么来的。

第三条（看板看不见工作树与 git 的分叉）核实成立，但**决定不做**：看板只反映本机状态，别人的机器脏不脏它看不到，加了反而给人虚假的安全感，成本却是每个工作区多一次子进程 + schema 字段 + 前端入口。

## 待办

- 待用户验收：`--no-sync` 写完要留下痕迹；下次撞 guard 时要看得出真因。

## 下一步

用户验收该看两条实测输出：`--no-sync` 写一笔后出现「本次按 --no-sync 未签入 git，N 个台账文件留在工作树里」；紧接着不带 `--no-sync` 再写一笔，报错开头变成「本地台账有还没签入 git 的改动（多半是上次用了 --no-sync，或上次提交/推送没成功）」。

## 过程

**改法只动文案与出口，不新增任何状态文件。** 「已写未提交」本来就是工作树状态，它天然持久；缺的只是有人把它说出来。

- `git_sync` 的 `--no-sync` 分支（`packages/skill/scripts/progress.py:848` 起）：先看 `CHANGED_FILES` / `PRESYNC_FILES` 里有没有真落盘的，有才打提示。纯只读式写入（内容没变）不吵。
- `_presync_guard` 的未提交分支（`:1130` 附近）：原因改成「还没签入 git（多半是上次用了 `--no-sync`，或上次提交/推送没成功）」，并给出三条出路：提交、丢弃、确认保留原样加 `--no-sync`。

**两条提示接得上**：第一条告诉你「这次没签」，第二条在你下次动手时告诉你「上次那笔还在」。因果闭环，不需要看板也不需要标记文件。

**验证。** 实测：`--no-sync` 写一笔 → `提示：本次按 --no-sync 未签入 git，2 个台账文件留在工作树里。下次写命令会先要求你提交它们。`；紧接着再写 → `错误：本地台账有还没签入 git 的改动（多半是上次用了 --no-sync，或上次提交/推送没成功）…`。smoke 里补了一条 `--no-sync 必须留痕` 断言，并把原来断言「未提交改动」字样的用例改成新文案。`npm run verify` 32 项通过；`koc-codelint` 六层全过（L3 经 `--fix` 后复跑）。

## 结论

- `--no-sync` 不再是静默路径：有实际改动就明确说「未签入 git」，并预告下次写会要求提交。
- guard 报错从「将被覆盖」改成「还没签入（上次 `--no-sync` 或提交失败）」，附带提交 / 丢弃 / `--no-sync` 三条出路。
- 看板侧不做 git 分叉探测（决定与理由记在背景节）：它只反映本机，收益不成比例。
