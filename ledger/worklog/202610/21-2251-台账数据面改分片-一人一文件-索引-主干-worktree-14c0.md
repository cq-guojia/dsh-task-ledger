`20261021-1147` 的 B5 条目当时已把替代方案写下来了：

> 任务按 hash 分桶成多个文件（重构成本大），或维持单文件、接受冲突并给明确的回收路径。

当时选了右边。**本任务改选左边**：放弃「事后合并冲突」，改成「让冲突没有发生的余地」。

### 已定稿（新方向）

1. **分片标识与文件名**（2026-10-21 拍板）
   - 标识主键 = `git var GIT_COMMITTER_IDENT` 里的 email（取不到再退回 `git config user.email`）；
     文件名 = `sha256(归一化主键)[:12] + ".json"`；索引 key 用归一化后的原始标识，保可读；
     分片文件内部自带 identity 字段（索引丢失时可自证）。
   - 判定依据是「这次操作要不要做 git 提交」，不是「有没有装 git」：
     目录在 git 仓库里 → 必须拿到 email，拿不到报错；不在仓库里 / 没装 git → 拿不到就用 default 并提示一次。
   - 实测依据：本地 commit 同样需要 email（不是只有推送需要）；`git var` 失败即 git 自己也提交不了（rc=128），
     所以报错是与 git 对齐而非额外限制；`git config user.email` 设成空字符串时 commit 仍成功
     （空值会 fallback 到 global），因此判定必须用 `git var` 而不是 `git config`。
   - 不用 MD5（招「不安全」的审查噪音，成本相同），改用 sha256 前 12 位。

2. **索引文件与分片布局**（2026-10-21 拍板）
   - 索引 `ledger/owners.json`、分片 `ledger/owners/<sha256前12位>.json`。
     索引留在 `ledger/` 根目录：host 的 `hasLedger` 要靠它当「这工作区有没有台账」的探测判据，埋进子目录就得多钻一层。
     定名 `owners` 而非 `workers`（与既有 `worklog/` 撞名）或 `index`（名不副实）。
   - 字段：`version` + `workers{ identity: { file, name, joined } }`。`name` 保留（邮箱太长，界面不好显示）。
     **不存任务数 / 最后活动**：每多一个会变的字段，索引就多一次被写的理由，会退化成第二个 `progress.json`。
   - `name` 自动检测，但只在真变了时才写索引（多数时候一个字节都不动，不会变成热点写点）。
     email 变了（主键）会分裂成两个分片，无法自动合并，手动处理。
   - **不做人员管理**：移除某人 = 手删索引条目 + 手删分片文件；不做 `left` 标记、不做归档目录、不做「我脱离了」。
     `validate` 只做双向校验并报出来（孤儿分片 / 索引指向不存在的文件），不自动处理。
   - 无 git / 不在仓库里时的兜底链：email → 系统用户名（`USER` / `LOGNAME` / `getpass.getuser()`，实测 `root`）
     → 主机名 → 字面 `default`。不用 `default@<主机名>`（容器 hostname 是随机 ID，实测 `7dc1fe732b7e`，重启即变）；
     字面 `default` 只作最后兜底并提示一次。

3. **公共池与退役**（2026-10-22 拍板）
   - 公共池 `ledger/pool.json`：装没人认领的，新任务一律先落这里；认领后搬进 `ledger/owners/<hash>.json`。
   - `ledger/progress.json` 退役：新布局上线后数据倒走，之后不再写。
     **旧项目不写迁移 / 兼容程序** —— 当前单人使用，落地后逐个项目手动迁（共五六个），用户 2026-10-22 重申。
   - 读侧口径：全量 = `pool.json` + `owners/*.json`，分片按索引定位、**不扫目录**（同第 2 条口径）；
     跨文件 id 去重；同一 tid 出现在多个文件就报出来（见下方第 5 条末段）。
   - **认领 / 释放一律搬文件**（2026-10-22 定）：认领 = 从 pool 搬进 `owners/<hash>.json`；
     释放（`set --status open`）= 搬回 pool。保持「pool = 全部未认领，owners/* = 各自认领的」单一不变量。
     顺序固定**先写后删**：崩在中间最多两边都有（读侧按 id 去重能兜），反过来就是任务凭空消失。
   - **代价（必须记住）**：`pool.json` 是公共写点，「一人一文件消除冲突」的收益在它身上不成立。
     新建与认领都写它，靠按任务号语义合并兜住（不同任务自动合）；
     但**两人同时认领同一任务**时，双方都在 pool 删同一行 → git 判为一致、不报冲突，
     两个分片各留一条 → 静默重复认领。用户 2026-10-22 裁定：**不解决**（几率极低，且写前本来就取版本）。

4. **history 层冲突与幂等**（2026-10-22 拍板）
   - **冲突走 union（两边都留）**：history 只增，冲突没有「该听谁的」—— 两边都是新记录，全留下就对。
     与 `worklog/` 同逻辑，复用 `_union_merge`（`progress.py:624`，`git merge-file --union`：相同行只留一份、两边新增行都留）。
     落点：`_resolve_ledger_conflict` 现在只接管 `progress.json` 与 `worklog/`（`progress.py:668-671`），
     加一个 `history/` 前缀判定即可 —— 不改写入姿势、不分片。
     ⚠️ 冲突**照样报**（末尾追加 = 同一插入点，git 必报 CONFLICT），区别是脚本接管自动合上、不再 abort 让人手改。
   - **`close` 写前查重（幂等）**：写 history 前按该行的过程文档链接查一次，写过就跳过写、直接删任务。

     写入顺序不用改 —— 现状已是「先写历史与过程文档，最后才从状态表移除」（`progress.py:2784-2790`）。
   - **跨月补录重复不管**：`--finished` 补录到另一月份时定位到别的文件、查不到 → 会留两条。
     用户 2026-10-22 裁定：不处理，不爽就手动删（纯历史查询，无影响）。
   - **「只增」的已知例外**：`upgrade_history`（`progress.py:1865`）会把老列数文件整体重写成 9 列

   - **实测依据**（`/tmp/hist`，bare 远端 + 两个 clone，全部真跑）：
     末尾追加（现状）→ `CONFLICT (content)`；插入相隔 6 行 → 自动合；相隔 1 行 → 自动合；同一行后插入 → `CONFLICT`。

5. **时间一律存 UTC**（2026-10-22 拍板）
   - **全链路统一 UTC**：任务号 / worklog 文件名、分片与 `pool.json` 内所有时间字段、`history` 行、
     分月归档 —— 全部 UTC，不带偏移量后缀（`2026-10-22 02:30:00`，语义即 UTC）。
   - **写入**：本地时间减掉偏移量后存（北京 10:30 → `02:30`）；`new --created` / `close --finished`

   - **读取 / 显示**：UTC + 查看者本地偏移。插件看板显示时转本地；`list` / `history` 的

## 过程

### 一、git 语义实证（临时 bare 仓库，`/tmp`）

三组实验的结论，全部有输出为证：

| 场景 | 实际行为 |
|---|---|
| 只改台账 → commit → push（远端已有他人提交） | `! [rejected] (fetch first/non-fast-forward)`，推不上去 |
| rebase 后 push | push 成功，但本地 `app.ts` 被静默替换成别人版本（别人的代码进了工作区，不是被覆盖） |
| 本地干净且落后 → 改台账 → `pull` | `Fast-forward`，他人代码与新增文件一起进来，未提交的台账改动原样保留 |
| 本地该文件有未提交改动且落后 → `pull` | `error: Your local changes would be overwritten` + `Aborting`，工作区不动 |
| 被拒后 `push --force` | 远端 `log` 从 `C2 → C1` 变 `C3 → C1`，他人的 `C2` 消失 |

**关键结论**：push 的判定依据是「你的提交是不是远端最新提交的后代」，与改了哪些文件无关。所以「我改的文件别人不碰就能直接推」不成立——照样被拒；但「别人不碰」意味着被拒之后 rebase 一定无冲突，一条命令自动接上。这就是分片方案的核心收益。

### 二、官方文档核实

| 来源 | 原文要点 |
|---|---|
| VS Code Source Control 文档 | `sync` = pulls before pushing（先拉后推），IDE 那个按钮就是 pull+push 两条命令 |
| JetBrains 帮助 | "Before you can share the results … you need to synchronize with the remote repository"；Update Project ≈ pull，merge 还是 rebase 由策略选 |
| `git-push` 手册 | `rejected` = "not a fast-forward and you did not force the update"；`--force-with-lease` 只在远端仍等于预期值时才覆盖 |
| `git-pull` 手册 | `pull` = fetch + integrate，整合方式四选一；冲突可 `--abort` |
| `gitattributes` | `merge=union` 是「两边行都留、顺序随机、无冲突标记」，会把 JSON 拼坏，**台账不能用** |

「推之前先取」是行业标准做法，不是谁乱来；但自动取只解决「接不上」，解决不了「两个人改同一处」。

### 三、代码勘察（两侧改动点）

**skill 侧（`packages/skill/scripts/progress.py`，147 KB）**

- `PROGRESS_REL` 常量与 `find_repo` 把「含 `ledger/progress.json` 的最近祖先」当作项目根判据 → 布局一变，所有工作区认不出来。
- `read_json` 硬校验顶层必须是 `{"tasks": {...}}`；`write_json` 强制「一任务一行 + key 字母序」（就是为了缩小 diff 冲突面）。
- 9 处命令级读写点（`cmd_new` / `cmd_claim` / `cmd_set` / `cmd_log` / `cmd_close` / `cmd_list` / `cmd_tags` / `cmd_validate` / `load_task`）全部按「一份文件」写。
- 任务号唯一性靠内存 dict 检查（`make_id` / `cmd_new`）→ 分片后只需查自己那份，跨人靠索引定位，**不需要全扫**。
- `git_presync` 的 `managed` 只含 `progress.json`（`close` 时加上当月 history）；`_resolve_ledger_conflict` 硬编码 `{ledger_rel}/progress.json`。
- 好消息：`_repo_lock_dir` 用 `--git-common-dir`，两个 worktree 共用一把锁，多检出场景已铺好路。

**host 侧（`packages/plugin/src/host/`）**

- `hasLedger()` = `existsSync(workspacePath/ledger/progress.json)`，是「这工作区有没有台账」的唯一判据，索引名一变 → 工作区从前端静默消失。
- `parseTaskList` 没有按 id 去重 → 跨分片重复 id 会统计双计，前端 `key` 也撞（`workspace.id + ':' + id`）。
- 合并**必须发生在脚本里**：host 不解析台账文件，只跑脚本吃 JSON；history 层已有现成范式（多文件 glob + 每行打 `src` 字段），照抄即可，host 近乎零改动。
- `cache` 是工作区级 1.5 秒 TTL，不是文件级 —— 不用改，别改成按文件缓存。

### 四、几个被否掉的方案

- **`merge=union` 驱动**：JSON 拼完即坏文件，不能用。
- **把用户名加进任务号**：任务号已经是「年月日-时分-标题-随机码」，再加人名会连带改 `ID_RE`、`--id` 规则、worklog 文件名、history 回链；而唯一性只需查自己那份就能保证，收益不成比例。
- **台账走分支**：台账是「现在谁在干什么」的现状，分支一分叉就有两套现状；而且看板读的是工作树，切到哪条分支看到的就是哪条分支的台账。**代码可以开分支，台账必须在主干**。
- **`--force`**：唯一会真正覆盖别人提交的路径，任何自动化里都不该出现。

## 结论

- **方向确定**：从「单文件 + 事后语义合并」改为「一人一文件 + 索引 + 台账固定主干（worktree 常驻）」。冲突不是被解决，是被消除。
- **能卸掉的负担**（都由单文件前提逼出来的）：整段仓级锁排队、写前定向预同步、rebase 冲突按 taskId 对账、autostash 兜底、业务代码 fast-forward。
- **必须保留**：git 守卫的 fail-closed、预同步失败回滚、原子写与权限/符号链接处理、`--no-sync` 留痕、同一人两台机器之间的 stash 叠回。
- **新增风险清单**（拆分自带的，必须配套）：
  1. 目录有文件但索引没列 → **静默漏任务**，不报错、`degraded` 也不触发 → `validate` 必须做索引↔目录双向校验。
  2. 索引丢失/为空 → 整个工作区从前端消失，比「少几个任务」更糟。
  3. 任务号唯一性从 O(1) 变「查自己那份」，跨人流转要靠索引定位。
  4. `close` 的 history 追加没有幂等键（既有缺口，与拆分无关，顺手补）。
- **工程量**：集中在 `progress.py` 的「定位 / 加载 / 落盘」三处抽象 + 索引一致性校验；host 侧只动 `hasLedger` 与 `parseTaskList` 去重。
