## Background

讨论中推翻了两个方案，都有代码依据：

1. **后端发广播**——不成立。`BroadcastChannel` 是浏览器 API，宿主进程没有；`dsh-plugin-core/src/runtime/notify.ts:171-182` 在无该全局时直接返回 `null`。

## Next

先定通用执行器的形状，再动代码。核心只需三类执行体 + 一个注册表：

- `shell`：`child_process.spawn(command, args, { cwd })`，stdout 逐行转进度，退出码即结果。node / python / bash / 任意二进制同属此类，不再细分（`exec` 不是另一类，只是同类的另一种底层实现，且缓冲输出、不适合长任务）。
- `executor:<name>`：使用方在 host 侧注册 Node 函数，前端只传短名 + 参数；核心按调用方插件补前缀（`dsh-task-ledger:tidy-files`），并校验「只能调自己注册的」。
- `agent`：起 DSH 会话（`workspace` + `prompt`），会话流式输出由核心转发。
- 前端永远只能传「名字 + 参数」；函数不能跨进程（`dsh-plugin-core/src/adv/tasks/pool.ts:83-102`：`run` 是函数，不进池、不过线）。
- **进度不做心跳**：执行器主动上报（`ctx.progress()` / stdout 行），宿主写进记录并由 SSE 推给页面。保活心跳属 SSE 层（`: ping` 注释行），使用方不实现，也不需要固定函数名。

## Process

- SSE 形态：`/follow` 是 `text/event-stream`，每个页面一条独立连接，宿主 `store.subscribe` 后逐条 `res.write`（`dsh-plugin-core/src/host/task-center.ts:136-162`）。
- 记录真源在内存 Map，不落盘；终态保留 10 分钟（`session-job.store.ts:29`），宿主重启即清空（`:156-161` 注释说明是刻意的）。
- Toast 由页面渲染，后台不参与：`dsh-plugin-core/src/ui/feedback/notify.ts:2-7`（纯投递，界面靠 `mountToasts()` 挂）。
- 广播型 Toast 不能带按钮：`dsh-plugin-core/src/ui/feedback/toast-queue.ts:68-79`（`actions?: never`，函数跨不了页）。
- 核心自带的广播接收端不按项目过滤——`notify-bridge.ts:49-58` 只取 title/level/detail，`message.project` 被丢掉，所以 `connectToasts()` 是全量收。
- 执行器注册表必须是宿主级单例（浏览器侧 `claimTaskNotifications` 用 `Symbol.for` 收口是同一手法），否则每个插件副本各一张表，跨插件调不到。
- 进度链路：执行器上报 → 记录 → SSE → 每个开着的页面各自渲染；页面关了就断，不做补投递（与终态通知同口径）。
- 前端不直连 agent 或脚本：会话归宿主持有，页面只是订阅者；现有 `session.service.ts:360-404` 已经是这个形状，缺的只是把 executor/shell 接进同一条记录链路。
- 任务列表按钮与 Toast 按钮**机制上没有区别**：都是 `id + 参数 → handlers[id](task)`。
  - 现状差异只是历史包袱：列表按钮多存了 `ServerTaskAction`（token/version + `/invoke`），而服务端只做校验并回 `detail`、不执行动作（`session-job.store.ts:319-330`）。
  - 页面本来就有完整记录（`status`、`detail`、`rowButtons`），可以自己按 `when` 过滤，**后端不必生成按钮**。
  - 结论：token/version/invoke 可删；统一为「发起方声明按钮（纯数据进记录），页面过滤渲染」。存的是声明，不是能力。

#### 统一契约（🆕 要加进 `adv/tasks` 的类型）

```ts
/**
 * 列表行按钮（`rowButtons`）。
 * 名字里带 row：这是**任务列表每一行**上的按钮，不是 Toast 上的按钮，也不是宿主动作。
 * 纯数据，跟着记录走到每个页面；谁渲染谁按 when 过滤。
 */
export interface TaskRowButtonSpec {
	readonly id: string;      // 必须是消费端 handlers 的键；本页没这个键 → 不画
	readonly text: string;    // 按钮文案
	readonly when?: TaskRowButtonWhen;   // 缺省 'always'
}
/** 记录状态只有三种（pool.ts:73），所以这里只会出现这三种 + always。 */
export type TaskRowButtonWhen = "running" | "done" | "failed" | "always";

/**
 * 广播范围。⚠️ 它不是网络层隔离：BroadcastChannel 一条通道全员都能收到，
 * 区别只在**广播内容里带不带 project、接收端按不按它过滤**。
 */
export type TaskBroadcastScope = "plugin" | "global";
// 'plugin'：广播里带 project，约定只有同 project 的消费者处理（别的插件也能收到，但它该忽略）
// 'global'：不按 project 过滤，任何监听者都可以处理（跨插件）

/** 一种终态（成功 / 失败各一份）。字段结构完全对称，所以能各自差异化。 */
export interface TaskNotifyLevelSpec {
	readonly title: string;                   // 主行，必填
	readonly description?: string;            // 次行，只能是字符串（函数跨不了页）
	readonly toast?: boolean;                 // 本页弹不弹，缺省继承 notify.toast
	readonly button?: { readonly id: string; readonly text: string };  // 本页 Toast 的按钮；不随广播走
	readonly broadcast?: TaskBroadcastScope;  // 省略 = 这一态不广播
}

/**
 * 终态提示。关键：**success / failure 各写各的，谁写了谁才有**。
 *   - 只写 success → 成功弹、失败不弹
 *   - 只写 failure → 失败弹、成功不弹
 *   - 两个都不写   → 都不弹（只留记录）
 */
export interface TaskNotifySpec {
	readonly toast?: boolean;                 // 总开关，false = 全都不弹（每态 broadcast 仍然生效）
	readonly success?: TaskNotifyLevelSpec;
	readonly failure?: TaskNotifyLevelSpec;
	readonly scope?: "all" | "origin";        // 弹给哪些页面：缺省 'all'；'origin' = 只有发起页弹
}

/** 发起一个后台任务 */
export interface StartTaskInput {
	readonly title: string;        // 列表标题 + 会话名
	readonly key?: string;         // 业务键，同键再发 = 就地更新
	readonly project?: string;     // 缺省全局项目
	readonly group?: string;       // 缺省 'default'
	readonly kind: "shell" | `executor:${string}` | "agent";   // 谁来执行
	readonly args?: unknown;       // 给执行器的参数，纯数据
	readonly notify?: TaskNotifySpec;
	readonly rowButtons?: readonly TaskRowButtonSpec[];   // 列表行按钮（不是 Toast 按钮）
}

/** TaskNotificationRecord 上要补的两个字段（其余字段见 pool.ts:143-184） */
// readonly rowButtons?: readonly TaskRowButtonSpec[];
// readonly progress?: { readonly done: number; readonly total: number; readonly tail?: string };

/** mountTaskUI 的入参（🆕）；project / groups 决定"收谁的任务" */
export interface MountTaskUIOptions {
	readonly project?: string | null;   // 字符串 = 只收该项目；null / 省略 = **全收（跨插件）**
	readonly groups?: readonly string[]; // 只收这些分组；省略 = 该项目下全收
	readonly handlers: Record<string, (task: TaskNotificationRecord) => void>;
	readonly onSettled?: (task: TaskNotificationRecord, outcome: "done" | "failed") => void;
}
```

```ts
/**
 * 本页作为「消费者」的全部接线，只在 apply() 里调一次。
 *
 * 这里只干两件事：
 *   ① 注册「按钮 id → 本页怎么处理」的映射 —— 列表按钮和 Toast 按钮都查这一份；
 *   ② 订阅本页能看到的任务终态 —— 弹 Toast、跑 onSettled。
 *
 * 这里**不**决定「哪个状态显示哪些按钮」：那是发起方在 startTask({ rowButtons }) 里写死的纯数据，
 * 渲染端只按 when 过滤（见第 3 处）。所以这个文件永远不会因为"多个页面按钮不一样"而改。
 */
import { mountTaskUI } from "dsh-plugin-core/ui/task-ui";          // 🆕 待核心实现
import type { TaskNotificationRecord } from "dsh-plugin-core/adv/tasks";
import { TASK_PROJECT, JOB_GROUP } from "./api";
import { openSession } from "./nav";                                // ✅ 已有（nav.ts:59）
import { openLogPanel } from "./board-home";                        // ✅ 已有预览 dock（见下方注）
import { startCloseTask } from "./close-task";
import { refreshBoard } from "./board-home";                        // 本插件需补的模块级刷新入口

/**
 * 从记录的 detail 里取一个字符串字段。
 *
 * 为什么要这个函数：`detail` 是「结构化可克隆的松散对象」（`TaskNotificationDetail`），
 * 类型上不保证有 sessionId / logPath —— 直接 `task.detail.sessionId` 编译不过，
 * 每处都写一遍 `as { sessionId?: string }` 又容易写错字段名还不报错。
 * 这里统一做三件事：断言一次、取不到不抛、非字符串（数字/对象/undefined）一律当没有。
 *
 * 取不到时调用方就"什么都不做"——宁可按钮点了没反应，也不要拿 undefined 去开会话/开文件。
 */
function field(task: TaskNotificationRecord, name: string): string | undefined {
	const detail = task.detail as Record<string, unknown> | undefined;
	const value = detail?.[name];
	return typeof value === "string" ? value : undefined;
}

/**
 * 按钮 id → 函数。**列表和 Toast 共用这一份**，所以不存在"列表能点、Toast 点了没反应"。
 * 这些函数只活在本页内存，不进记录、不跨页（pool.ts:161-162）。
 * 一个 id 在本页没注册 → 列表和 Toast 都不画它，不会出现死按钮。
 */
export const taskHandlers: Record<string, (task: TaskNotificationRecord) => void> = {
	// 跑着的时候看会话（只有 agent 执行体有 sessionId；executor / shell 没有）
	"open-session": (task) => {
		const sessionId = field(task, "sessionId");
		if (sessionId !== undefined) openSession(sessionId);
	},

	// 看这次执行的日志。走本插件已有的预览 dock，不新起第二个预览面。
	// ⚠️ 落地时要做的一件小事：board-home.ts 里 openPreview 现在是组件内闭包（用 mountRef），
	//    把它提升成模块级导出 openLogPanel(path) 即可，逻辑不动。
	"open-log": (task) => {
		const logPath = field(task, "logPath");
		if (logPath !== undefined) openLogPanel(logPath);
	},

	// 重跑：参数从记录里取，不从闭包取 —— 这条记录可能是别的页面发起的，
	// 本页没有当时的任何局部变量，唯一能依赖的就是记录本身。
	"retry": (task) => {
		const taskId = field(task, "taskId");
		const workspace = field(task, "workspace");
		if (taskId === undefined || workspace === undefined) return;
		void startCloseTask({ taskId, workspace });
	},
};

export function mountLedgerTaskUi(): void {
	mountTaskUI({
		// 收谁的任务 —— 这是「本插件 vs 跨插件」的唯一开关：
		//   写 project 字符串 → 只收这个项目的（本插件现在这样）
		//   写 null / 不写     → 收所有项目的任务（跨插件；别人的按钮没 handler 就不画）
		// 必须与 startTask 的 project 逐字一致：写错不报错，只是永远收不到。
		project: TASK_PROJECT,

		// 只收这个分组；不传 = 该项目下全收。台账只有一组，在这里就收窄。
		groups: [JOB_GROUP],

		handlers: taskHandlers,

		// 终态回调：成功失败都刷（失败也要把"执行中"改掉）。
		// 只放数据刷新，别在这里弹第二个提示 —— 提示已经由 notify 那段负责了。
		// ⚠️ 落地时同样要补一个模块级 refreshBoard（现在是 board-home 组件内的 refresh）。
		onSettled: (_task, _outcome) => {
			refreshBoard();
		},
	});
}
```

#### 第 2 处：`client/close-task.ts` —— 发起（每次点击调用）

```ts
/**
 * 发起一次结案。每次点击调一次。
 *
 * 「这个任务长什么样」全在这里说完：干什么、弹什么、列表上给哪些按钮。
 * 这些东西是**纯数据写进记录**跟着走的，所以另一个页面即使没打开过这个组件，
 * 也能画出同样的按钮、弹出同样的提示 —— 它只需要有同名的 handlers。
 */
import { startTask } from "dsh-plugin-core/adv/tasks";   // 🆕 新入口
import { TASK_PROJECT, JOB_GROUP } from "./api";

export interface CloseTaskInput {
	readonly taskId: string;
	readonly workspace: string;
	readonly note?: string;
}

export async function startCloseTask(input: CloseTaskInput): Promise<void> {
	await startTask({
		project: TASK_PROJECT,
		group: JOB_GROUP,
		title: `结案 ${input.taskId}`,     // 列表标题 + 会话名（agent 执行体直接拿它开会话）
		key: `close:${input.taskId}`,      // 业务键：同一任务再点 = 就地更新，不堆两条

		// 谁来执行：宿主侧注册的 executor（host/executors/close-task.ts）
		kind: "executor:close-task",

		// 给执行器的参数。只能是纯数据：函数、类实例、DOM 都过不了进程边界（pool.ts:83-102）。
		args: input,

		// ① Toast：弹什么卡。也能跨页、跨项目 —— 与 notify 一样每态各配一个 scope。
		//    scope 'all'      = 每个开着的页面都弹（含别的项目的页面，核心自动不画它没 handler 的按钮）
		//    scope 'origin'   = 只有发起页弹
		//    跨项目不需要额外开关：接收端 mountTaskUI({ project: null }) 就收得到，按钮按 handler 自动隐藏。
		//    不写 toast.<态> = 该态不弹。
		toast: {
			success: {
				title: "任务已结案",
				button: { id: "open-log", text: "看日志" },
				scope: "all",          // 成功：所有页面都弹（跨页 / 跨项目）
			},
			failure: {
				title: "结案未完成",
				button: { id: "retry", text: "重跑" },
				scope: "origin",       // 失败：只有发起页弹
			},
		},

		// ② 通知：发一条消息出去。成功 / 失败各配一条，各管各的范围和广播。
		//    scope = 谁会弹这条通知；broadcast = 走不走跨页通道。两者都能按状态分开配。
		notify: {
			success: {
				message: "结案完成",                       // 通知正文
				detail: { taskId: input.taskId },          // 附带的纯 JSON，接收端自己取
				scope: "all",                              // all = 所有页面弹；origin = 只有发起页弹
				broadcast: "plugin",                       // plugin = 同项目；global = 跨插件；不写 = 不广播
			},
			failure: {
				message: "结案失败，请重跑",
				detail: { taskId: input.taskId },
				scope: "origin",                           // 失败只在发起页弹，与成功不同
				broadcast: "global",
			},
		},

		// ② 列表行按钮（rowButtons）：纯数据跟着记录走，when 决定哪个状态显示。
		//    名字带 row = 画在任务列表每一行上；Toast 的按钮在上面 notify 里，两者互不影响。
		//    同一个 id 可以在不同 when 上重复声明（下面 open-log / retry 各出现两次）。
		//    ⚠️ 只有记录还在列表里才画得出来：看板目前"跑完就撤行"，
		//       所以 done / failed 的按钮只在终态保留窗口内可见（见下方说明）。
		rowButtons: [
			{ id: "open-session", text: "查看",   when: "running" },
			{ id: "open-log",     text: "看日志", when: "done" },
			{ id: "retry",        text: "重跑",   when: "done" },
			{ id: "open-log",     text: "看日志", when: "failed" },
			{ id: "retry",        text: "重跑",   when: "failed" },
		],
	});
}
```

三个必须知道的点：

- `await startTask(...)` 等的是**登记成功**，不是任务跑完 —— 后台任务的天性，别写 `await` 之后去读结果。
- `notify` 和 `rowButtons` 都是**写给所有页面看的**：哪个页面打开着，就按同一份配置渲染。所以别把"只有本页才有的 id"写进去当私有按钮。
- **`when: "done" / "failed"` 的按钮，只有记录还在列表里时才看得到。** 本插件看板现在是「跑完就撤行」，
  所以这两组按钮实际看不到；想让它们可点，就得把终态记录留一小段（10–30 秒）再移除 ——
  这就是"成功了还能点重跑"的做法，属列表展示策略，不改记录本身（核心的终态记录本来就保留 10 分钟）。

#### 第 3 处：`client/index.ts` —— 列表用核心控件，本插件不画 UI


**画面归核心，不归本插件**：第 3 处只传配置，渲染交出去。以后核心改样式、改进度展示、改筛选，
本插件这三行不用动。能由使用方声明的只有「按钮 id / 文案 / when」，它们跟着记录走，不属于画面。

#### `when` 的匹配规则（就四条）

| `when` | 什么时候显示 |
|---|---|
| `"running"` | `task.status === "running"` |
| `"done"` | `task.status === "done"` |
| `"failed"` | `task.status === "failed"` |
| `"always"` 或不写 | 任何状态都显示（如「打开会话」） |

`status` 只有这三个值（`pool.ts:73`：`'running' \| 'done' \| 'failed'`），所以 `when` 不会有第四种。
两套按钮不冲突：**Toast 只认 `notify.success.button` / `notify.failure.button`（各一个），列表只认 `rowButtons`（多个 + when）**，两者都靠同一个 `handlers` 找函数。

#### 「本插件 / 跨插件」和「要不要广播」是两个独立开关

| 想要的效果 | 怎么配 | 说明 |
|---|---|---|
| 只收本插件的任务 | `mountTaskUI({ project: TASK_PROJECT })` | 本插件现在这样 |
| 收**所有插件**的任务（跨插件） | `mountTaskUI({ project: null })` 或干脆不写 `project` | 核心的查询侧本来就支持「不按项目过滤」（`resolveProject(null)` → `null`） |
| 跨插件收到别人的任务，但不想显示别人的按钮 | 什么都不用做 | 别人的按钮 id 本页没有 handler → 自动不画（第 3 处那段 filter） |
| 本插件弹、别的插件不弹 | 发起方不动；别的插件的 `mountTaskUI` 只要写了自己的 `project` 就收不到 | 过滤发生在**接收方**，不是发送方喊给谁 |
| 成功/失败各自决定弹不弹 | `notify.success.toast` / `notify.failure.toast`；整态不给就是"不弹" | `notify.toast` 是总开关 |
| 成功广播、失败不广播 | `notify.success.broadcast: 'plugin'`，`failure` 不写 `broadcast` | 每态独立 |
| 广播给同项目的消费者 | `broadcast: 'plugin'` | 消息里带 `project`，约定同项目才处理 |
| 广播给所有插件 | `broadcast: 'global'` | 不按 `project` 过滤 |

⚠️ 两件事别混：
- `project` 过滤 = **我愿不愿意看别人的任务**（接收端设置）。
- `broadcast` = **我这条终态要不要喊出去**（发送端设置）。
- 广播不是"点对点"：`BroadcastChannel` 一条通道全员都能收到，`'plugin'` / `'global'` 的区别只在**消息里带不带 project、接收端按不按它过滤**。

#### 想监听广播：自己订阅（核心不给默认行为）

```ts
/**
 * 广播接收端：谁想处理谁订阅。核心只负责"发出去"，不替任何人决定收到后干什么
 * （`ui/feedback/notify.ts` 里那个 connectToasts 是"收到就弹一条"的另一种选择，不是默认）。
 */
import { subscribeNotifications } from "dsh-plugin-core/runtime";   // ✅ 已有
import { TASK_PROJECT } from "./api";

export function listenTaskBroadcast(onChange: () => void): () => void {
	return subscribeNotifications((msg, remote) => {
		// remote=false 是本页自己发的（notifyMessage 会先给本页一份），需要去重就靠它。
		// 'plugin' 范围：只处理本项目的；'global' 范围：不限项目，下面这行去掉即可。
		if (msg.project !== TASK_PROJECT) return;
		// 业务信号放 detail（纯 JSON），按它分派；level 是提示色调，不要当业务类型用。
		onChange();
	});
}
```

**广播里能带什么**：`title`、`description`（进 `detail`）、`level`、`project`、`group` —— 就这些，
**带不了按钮**（函数跨不了页，`toast-queue.ts:68-79` 类型上是 `actions?: never`）。
所以"成功了广播什么"= 一条标题 + 一句描述 + 色调；要按钮只能在**本页 Toast** 上点。

#### 广播：默认关，别当主通知

**一、要不要广播？默认值是什么？**

| 场景 | 走什么 | 默认 |
|---|---|---|
| 任务终态通知（本方案主职） | 宿主记录 + SSE | **不广播**，`notify.<态>.broadcast` 不写 |
| 终态弹不弹卡片 | `notify.toast` | `true` |
| 弹给所有页面还是只发起页 | `notify.scope` | `'all'` |
| 不落记录的临时提示（"已复制"/"连接已恢复"） | `notify({ broadcast: true })` 或干脆本页 | 本页 |
| 跨 window / iframe / 非 SSE 消费者 | `BroadcastChannel` | 用的时候才开 |

为什么任务通知不该广播：宿主已经对**每条** SSE 连接各推一份终态（`host/task-center.ts:145-154`），
再加一条 `BroadcastChannel` 就是同一件事走两条线，每个页面收两遍 → 弹两条。**没有"要不要"的问题，是不需要。**

**二、广播要配哪些参数？**

| 参数 | 类型 | 默认值 | 含义 / 为什么 |
|---|---|---|---|
| `notify.success.broadcast` / `notify.failure.broadcast` | `'plugin' \| 'global'` | 无 = 该态不广播 | 每态独立；`'plugin'` 带 project、同项目才处理，`'global'` 跨插件。开之前先问：SSE 为什么不够 |
| `notify.scope` | `'all' \| 'origin'` | `'all'` | 只影响"弹不弹"，不影响"记录有没有"；`'origin'` 靠 `record.origin`（`pool.ts:167`）判断是不是发起页 |
| `notify.toast` | `boolean` | `true` | 总开关；`false` = 两种终态都不弹（广播仍按每态配置走） |
| `notify.success.toast` / `failure.toast` | `boolean` | 继承 `notify.toast` | 单态开关；配合"整态不写"可做到只成功弹 / 只失败弹 |
| `notify.success` / `failure` | `{ title, description?, button?, broadcast? }` | 不写 = 该态无提示 | `description` 只能是字符串（跨页要能克隆，`ui/feedback/notify.ts:99-102` 对非字符串直接抛） |
| `notify.success.button` / `failure.button` | `{ id, text }` | 无 | 每态各自一个按钮；`id` 必须是本页 `handlers` 的键；**广播路径禁止带按钮**（`toast-queue.ts:68-79` 类型上 `actions?: never`） |
| 通道名 | 由核心固定（`NOTIFY_CHANNEL`） | — | 任务通知不给配。改名 = 换协议，旧页面收不到（`runtime/notify.ts:21-23`） |
| `project` / `group` | `string` | 默认项目 / `'default'` | **这才是"发给谁"的开关**，不是广播开关 |

**三、广播发到哪？当前发起的插件实例，还是所有？**

分两层看，**都不存在"按插件实例"这种分区**：

| 层 | 谁收得到 | 收不到谁 |
|---|---|---|
| SSE（默认路径） | 所有连到**同一宿主**的页面：同窗口多标签、不同窗口、不同 workspace 都算 | 宿主没连上的页面；页面关了不做补投递 |
| `BroadcastChannel`（`broadcast: true`） | **同一 origin** 的所有 window / tab / iframe | 别的端口 / 域名；宿主进程（Node 没有这个 API，`runtime/notify.ts:171-182` 无该全局时返回 `null`） |

两个必须写进注释的事实：

1. **广播没有"只发给发起者"这回事**。`BroadcastChannel` 收不到自己 post 的消息，所以本页要靠
   "自己发出的消息回流"（`remote: false`）才弹一次 —— 一旦发出去，同源所有页面都会收到。
   想只让发起页看见，靠的是 `scope: 'origin'` 过滤，不是靠广播范围。
2. **N×N 风险只在页面侧发起时存在**：3 个页面各发一次 = 每页收 3 条 = 9 条。
   所以广播的规矩是「**只由发起页发一次，接收页只收不发**」；服务端抢占标记那一套不需要，
   因为服务端根本没有 `BroadcastChannel`（`runtime/notify.ts:165-182`）。

**四、本插件要不要用广播？** 任务通知不用（不写 `broadcast`），
但**「一个页面改了东西，别的页面跟着变」这个场景要用**，而且用一条自建的裸通道 —— 见下一节。

#### 跨页面刷新信号：三处代码（广播唯一真正值得用的地方）

**场景**：在 A 页面改了一条任务（结案 / 改标签 / 改备注 / 批量操作），B、C 页面开着的看板、
统计、侧栏都得跟着变。但这些页面**不一定挂着那个组件** —— 组件级订阅够不着它们。
能兜住的是 `apply()`：它一定跑过。所以订阅必须挂在 `apply`，不能挂在组件里。

**为什么不用核心的 `notifyMessage` 发这个信号**：
`notifyMessage` 是给「提示」用的，它的接收端 `connectToasts()` **不按 project 过滤**
（`ui/feedback/notify-bridge.ts:49-58` 只取 title/level/detail，把 `message.project` 丢掉），
所以任何页面只要接过 `connectToasts()`，你这条静默信号都会**顺带弹一张卡片**。
静默刷新就用一条自己的裸通道，10 行，谁也不打扰。

```ts
/* ═════════ 第 1 处：client/sync.ts —— 一个文件放下「发」和「收」 ═════════
 * 这个文件不认识任务、不认识 UI，只干一件事：告诉同源的其它页面「数据变了，重新取」。
 * 它不传数据本身，只传一个信号 —— 数据还是各页面自己去宿主取（避免大对象跨页、避免过期副本）。
 */
const CHANNEL = "dsh-task-ledger/sync/v1";
// 名字必须带插件前缀：BroadcastChannel 的命名空间是**整个 origin**，
// 所有插件共用一个池子，不带前缀必撞车（撞了就是收别人的消息）。
// 名字带 /v1：消息格式变了就升版，旧页面自然收不到新消息 —— 好过收到不认识的结构再崩。

/** 信号：只有一种「变了」。后续要分种类就加 type 值，别改字段名。 */
export interface LedgerChanged {
	readonly type: "ledger-changed";
	/** 哪个 workspace 变了；省略 = 不区分（收到就全刷）。 */
	readonly workspace?: string;
}

/**
 * 发：改完台账调一次。
 *
 * 🚨 本页**收不到自己发的这条**（BroadcastChannel 的硬规则：收不到自己 post 的消息），
 *    所以调用处必须自己先刷新一次，别指望广播回来 —— 这是最容易漏的一行。
 * 通道用完立刻 close：长驻一条通道会一直被事件循环保活，页面关了也不释放。
 */
export function announceChanged(workspace?: string): void {
	// Node / 老环境没有这个 API：静默跳过（不是错误，宿主侧本来就发不了广播）。
	// 不写这个判断，整个模块在 Node 单测里 import 就炸。
	if (typeof BroadcastChannel === "undefined") return;
	const channel = new BroadcastChannel(CHANNEL);
	try {
		channel.postMessage({ type: "ledger-changed", workspace } satisfies LedgerChanged);
	} finally {
		channel.close();
	}
}

/**
 * 收：页面加载时（apply 里）调一次，返回退订函数。
 * 回调里只做「重新取数据」这一件事，不要在这里操作 DOM / 弹窗 —— 那个归 UI 层。
 */
export function listenChanged(onChange: (signal: LedgerChanged) => void): () => void {
	if (typeof BroadcastChannel === "undefined") return () => {};
	const channel = new BroadcastChannel(CHANNEL);
	channel.onmessage = (event: MessageEvent<unknown>) => {
		// 跨页只能过结构化克隆的纯数据，且同一个 origin 上有别人的消息：
		// 认不出 type 就丢，不要 try/catch 硬扛，也不要假设字段齐全。
		const data = event.data as Partial<LedgerChanged> | null;
		if (data?.type !== "ledger-changed") return;
		onChange({ type: "ledger-changed", workspace: data.workspace });
	};
	return () => {
		channel.onmessage = null;
		channel.close();
	};
}

/* ═════════ 第 2 处：client/index.ts 的 apply() —— 接一次，插件级 ═════════
 * 只加这一坨，位置在 setDefaultTaskProject / setTaskBackend 之后。
 */
export function apply(ctx: ClientContext): void {
	setDefaultTaskProject(TASK_PROJECT);          // ✅ 已有（client/index.ts:216）
	// ...taskNotifications.setTaskBackend(...) / connectHost(ctx) 等原有接线

	// 收到别的页面的信号 → 本页重新取一遍台账。
	// 为什么在 apply 而不是组件里：看板可能没打开，但 apply 一定跑过（这是本需求的关键）。
	// ctx.effect 的返回值是清理函数，页面/插件卸载时自动退订 + 关通道。
	ctx.effect(() =>
		listenChanged((signal) => {
			// workspace 有值就只认它；没值表示「不区分」，全刷。
			if (signal.workspace !== undefined && signal.workspace !== currentWorkspace()) return;
			void refreshLedger();   // 简单版：整体重取。不要在这里做增量合并（先跑通再加）
		}),
	);
}

/* ═════════ 第 3 处：改完台账的地方（结案回调 / 设置保存 / 批量操作）═════════
 * 每个「写」的落点加两行：先自己刷，再广播。
 */
async function onLedgerWritten(workspace: string): Promise<void> {
	await refreshLedger();        // 1) 本页先刷（广播收不到自己，别漏）
	announceChanged(workspace);   // 2) 再通知其它页面；没人开着就没人收，不做补投递
}
```

**这条通道的边界（写死在注释里，免得以后踩）**

| 事实 | 含义 |
|---|---|
| 同源 = 同协议+域名+端口 | 开在另一个端口的 DSH、另一台机器上的，收不到 —— 那种要宿主推（SSE 已有这条线） |
| 只有**页面**能发 | 宿主进程没有 `BroadcastChannel`，所以「后台跑完通知所有页面」不能靠它 |
| 页面关了收不到，也不补投递 | 与 SSE 同口径；靠"打开时重新拉数据"兜底，不靠"消息不丢" |
| 收不到自己 | 发送处自己必须刷一次，这是唯一必须记住的坑 |
| 消息必须能结构化克隆 | 函数、DOM、类实例过不去；只传纯数据（信号本来就只有字符串） |
| 只传信号、不传数据 | 数据各页面自己拉，避免体积、避免拿到过期副本、避免两个页面数据不一致 |

**为什么"页面广播"只是够用而不是最优**：如果改动本身是写进宿主配置的，最正确是**宿主推**
（`/follow` 那条 SSE 已经在推任务记录）；页面广播依赖"每个页面都装了本插件且都跑过 apply"，
适合"页面内改、页面间同步"这种低风险场景。别拿它当跨进程通知用。

### 全量配置清单（用不上的也列出来，写清为什么）

**A. 自建信号通道（本节推荐，用于"改了东西让所有页面跟着变"）**

## Conclusion

已定稿（十六条）：

1. 后台只存状态，**不发通知**；没有「后端发广播」这回事。
2. 页面订阅 SSE 长连接拿终态，**各自**渲染 Toast；开 3 个页面就各弹 1 条，不用抢、不用广播。
3. 调用时把 `toast`（本页弹什么卡）和 `notify`（发什么通知、发给谁、`plugin`/`global` 广播）**分开配**，两者都按成功/失败各写一份；某态不写 = 该态不做。
4. 按钮是本页函数，**本页没注册就不画**；别的页面天然不受影响。
5. 刷新后的可点性 = 记录还在 + 初始化代码重跑（重新注册 handlers），不存「已展示」标记。
6. 使用方只写两处：`mountTaskUI`（一次，监听 + handlers）、`startTask`（每次，传 notify + rowButtons）。
7. **进度不用心跳**：执行器主动上报，核心只转发；三类执行体的进度统一成「行/百分比 + 日志尾部」。
8. 前端只订阅核心，不直连 agent 或脚本；会话与进程都属于宿主，页面只是观众。
9. 报不报进度由执行器决定：不报也能跑完、也能通知，代价只是长任务看起来像卡住。
10. 广播降级为可选通道：主通知走 SSE，`notify.<态>.broadcast` 缺省不写（= 不广播）；广播只服务跨 window / iframe / 非 SSE 消费者，且启用时必须解决 N×N 重复（只由发起页发一次）。
11. 消费端最终只写 2 处必选（入口挂载 + 发起调用），执行器注册或脚本二选一，UI 展示可选。
12. 列表行按钮（`rowButtons`）与 Toast 按钮**无机制区别**：都是 `id + 记录 → handlers[id](task)` 同一段程序。按钮由发起方在 `startTask({ rowButtons })` 里声明（纯数据、存进记录、宿主不解释不校验），渲染端只按 `when` + 本页 `handlers` 过滤；后端不生成按钮、不存 token。
13. **两套按钮分开配、能不一样**：Toast 按钮在 `notify.success.button` / `notify.failure.button`（各一个，成功失败可不同），列表行按钮在 `rowButtons`（多个 + when）。`notify.success` / `failure` 不写就是不提示，所以「只成功弹」「只失败弹」天然支持。
14. **「本插件还是跨插件」与「要不要广播」是两个开关**：收谁的由 `mountTaskUI.project`（`null` = 全收）决定；喊不喊由 `notify.<态>.broadcast`（`'plugin'` / `'global'`）决定。广播不带按钮，要按钮只能点本页 Toast。
15. **广播没有「只发给发起插件实例」这回事**：分区键只有 `project` + `group`，不是发起者。SSE 到同宿主所有页面，`BroadcastChannel` 到同源所有 window / iframe；「只让发起页看见」用 `notify.scope: 'origin'` 在接收端过滤，不是靠缩小广播范围。
16. **「改了东西让所有页面跟着变」用自建裸通道，不走 `notifyMessage`**：后者接收端 `connectToasts()` 不按 project 过滤，静默信号会顺带弹卡片。三处落地 = `client/sync.ts`（发 + 收）、`apply()` 里 `ctx.effect(() => listenChanged(...))`、每次写成功后 `announceChanged(workspace)` + 本页先自己刷（本页收不到自己发的消息）。

执行侧未定：只有 agent 会话一种执行体，通用后台任务（shell / 自定义执行器）尚无实现。
