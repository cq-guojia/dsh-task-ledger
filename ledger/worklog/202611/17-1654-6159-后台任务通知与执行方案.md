## Next

先定通用执行器的形状，再动代码。核心只需三类执行体 + 一个注册表：

- `shell`：`child_process.spawn(command, args, { cwd })`，stdout 逐行转进度，退出码即结果。node / python / bash / 任意二进制同属此类，不再细分（`exec` 不是另一类，只是同类的另一种底层实现，且缓冲输出、不适合长任务）。
- `executor:<name>`：使用方在 host 侧注册 Node 函数，前端只传短名 + 参数；核心按调用方插件补前缀（`dsh-task-ledger:tidy-files`），并校验「只能调自己注册的」。
- `agent`：起 DSH 会话（`workspace` + `prompt`），会话流式输出由核心转发。
- 前端永远只能传「名字 + 参数」；函数不能跨进程（`dsh-plugin-core/src/adv/tasks/pool.ts:83-102`：`run` 是函数，不进池、不过线）。
- **进度不做心跳**：执行器主动上报（`ctx.progress()` / stdout 行），宿主写进记录并由 SSE 推给页面。保活心跳属 SSE 层（`: ping` 注释行），使用方不实现，也不需要固定函数名。

## Process

- SSE 形态：`/follow` 是 `text/event-stream`，每个页面一条独立连接，宿主 `store.subscribe` 后逐条 `res.write`（`dsh-plugin-core/src/host/task-center.ts:136-162`）。
- 记录真源在内存 Map，不落盘；终态保留 10 分钟（`session-job.store.ts:29`），宿主重启即清空（`:156-161` 注释说明是刻意的）。
- Toast 由页面渲染，后台不参与：`dsh-plugin-core/src/ui/feedback/notify.ts:2-7`（纯投递，界面靠 `mountToasts()` 挂）。
- 广播型 Toast 不能带按钮：`dsh-plugin-core/src/ui/feedback/toast-queue.ts:68-79`（`actions?: never`，函数跨不了页）。
- 核心自带的广播接收端不按项目过滤——`notify-bridge.ts:49-58` 只取 title/level/detail，`message.project` 被丢掉，所以 `connectToasts()` 是全量收。
- 执行器注册表必须是宿主级单例（浏览器侧 `claimTaskNotifications` 用 `Symbol.for` 收口是同一手法），否则每个插件副本各一张表，跨插件调不到。
- 进度链路：执行器上报 → 记录 → SSE → 每个开着的页面各自渲染；页面关了就断，不做补投递（与终态通知同口径）。
- 前端不直连 agent 或脚本：会话归宿主持有，页面只是订阅者；现有 `session.service.ts:360-404` 已经是这个形状，缺的只是把 executor/shell 接进同一条记录链路。
- 任务列表按钮与 Toast 按钮**机制上没有区别**：都是 `id + 参数 → handlers[id](task)`。
  - 现状差异只是历史包袱：列表按钮多存了 `ServerTaskAction`（token/version + `/invoke`），而服务端只做校验并回 `detail`、不执行动作（`session-job.store.ts:319-330`）。
  - 页面本来就有完整记录（`status`、`detail`），可以自己按状态决定画哪些按钮，**后端不必存按钮**。
  - 结论：token/version/invoke 可删；统一为「后端存状态，页面画按钮」。

**先说死广播（回答「默认要不要、配什么、发给谁」）**：

- **默认不广播**，任务终态通知也**不需要**广播。它走的是「页面 `startTask` → host 记录 → SSE」，
  宿主对**每条** SSE 连接各推一份（`host/task-center.ts:145-154`），本身就已经覆盖所有开着的页面。
- `broadcast` 只留给「**不落记录的纯提示**」和「**非 SSE 消费者**（跨 window / iframe / 外部页面）」，
  缺省 `false`；打开它等于多加一条并行链路，必须自己防重复。
- 「广播给谁」分两层，**不是按插件实例分**，详见本节末尾《广播：默认关，别当主通知》。

```ts
/* ───────── 0. client/nav.ts：按钮实现表（列表与 Toast 共用同一份） ─────────
 * 为什么必须是一张表：按钮的输入只有「id + 记录」两样，列表和 Toast 都要同一套行为。
 * 两边各写一份必然分叉（典型症状：列表里"重跑"能点，Toast 里点了没反应）。
 * 表里的函数只活在本页内存，不进记录、不跨页 —— 见 pool.ts:161-162「方法本身留在创建页内存里」。
 */
import type { TaskNotificationRecord } from "dsh-plugin-core/adv/tasks";   // ✅

export const buttonHandlers: Record<string, (task: TaskNotificationRecord) => void> = {
	// 键名用字符串常量，不用数组下标：这个 id 要写进记录、跨进程序列化，
	// 数字下标在两侧数组顺序不同步时会静默指到错按钮（点了打开别的东西，比点了没反应更难查）。
	// 键名 == startTask({ notify: { button: { id } } }) 里的 id，改名字必须两边一起改。

	// 打开这条任务对应的会话（agent 执行体才有 sessionId；shell / 自定义执行器没有）
	"open-session": (task) => {
		// detail 是「结构化可克隆的松散对象」（TaskNotificationDetail），按需断言取字段；
		// 取不到就什么都不做 —— 宁可按钮点了没反应，也不要拿 undefined 去开一个空会话。
		const detail = task.detail as { sessionId?: string } | undefined;
		if (detail?.sessionId !== undefined) openSession(detail.sessionId);
	},

	// 打开这次执行的日志（shell / executor 执行体由核心写 logPath）
	"open-log": (task) => {
		const detail = task.detail as { logPath?: string } | undefined;
		if (detail?.logPath !== undefined) void openFile(detail.logPath);
	},

	// 重跑一次：参数从 detail 里取，不从闭包取 —— 这条记录可能是别的页面发起的，
	// 本页没有发起时的任何局部变量，唯一能依赖的就是记录本身。
	"retry": (task) => {
		const detail = task.detail as { taskId?: string; workspace?: string } | undefined;
		if (detail?.taskId !== undefined && detail.workspace !== undefined) {
			void startCloseTask({ taskId: detail.taskId, workspace: detail.workspace });
		}
	},
};

/* ───────── 1. client/index.ts：入口挂载（整个插件一次） ─────────
 * 只挂一次，挂在 apply() 里。这是「本页作为消费者」的全部配置：
 * 收哪些任务、收完干什么、按钮点哪个函数 —— 三件事都只在这里说一遍。
 */
import { mountTaskToasts } from "dsh-plugin-core/ui/task-toast";   // 🆕
import { buttonHandlers } from "./nav";

export function apply(ctx: ClientContext): void {
	// ...原有 setDefaultTaskProject / setTaskBackend / connectHost ...

	mountTaskToasts({
		// 过滤器 1：只收本插件的任务。project 是记录的第一级分区键（pool.ts:147-148），
		// 必须与 startTask 传的 project 逐字一致 —— 写错了不报错，只是永远收不到。
		project: TASK_PROJECT,

		// 过滤器 2：只收这些分组。组是第二级分区（pool.ts:149-150，缺省 'default'）；
		// 不传 = 该 project 下全收。台账只用 JOB_GROUP 一组，所以在这里就收窄。
		groups: [JOB_GROUP],

		// 终态回调：写盘 / 刷列表这类收尾动作放这里，不要塞进 Toast 的按钮里。
		// outcome 只有 'done' / 'failed' 两种；失败也要刷（状态要从"执行中"变过去）。
		onSettled: (task, outcome) => {
			void refresh();                      // 成功失败都刷新看板，别只判 done
		},

		// 按钮实现：与列表共用同一份表，见第 0 段。
		// 本页没注册的 id 就不画按钮（内部按 handlers 存在与否过滤），不会出现"点了没反应"。
		handlers: buttonHandlers,
	});
}

/* ───────── 2. client/close-task.ts：发起（每次点击） ─────────
 * 这是「本页作为发起方」的全部配置。notify 整块写进宿主记录，由每个页面自己解释：
 * 核心不认识 title/button 的语义，只当纯数据存和转发（同一个任务在每个页面弹出同样的文案）。
 */
import { startTask } from "dsh-plugin-core/adv/tasks";   // ✅ 入参；notify 字段 🆕

export function startCloseTask(input: {
	taskId: string;
	workspace: string;
	note?: string;
}) {
	return startTask({
		title: `结案 ${input.taskId}`,       // ✅ 列表显示名 + 会话名，两个地方都用它
		key: `close:${input.taskId}`,        // ✅ 业务键：同键再点一次是"就地更新"，不会堆两条
		group: JOB_GROUP,                    // ✅ 第二级分区，必须与 mountTaskToasts 的 groups 对得上
		kind: "executor:close-task",         // 🆕 执行体选择：executor:<注册名> / shell / agent
		args: input,                         // 🆕 纯数据进记录（函数不能跨进程，见 pool.ts:83-102）

		// ── 通知配置（🆕 整块新增）─────────────────────────────────────────
		notify: {
			// 终态要不要弹卡片。缺省 true；批量/低价值任务给 false，只留记录不打扰。
			toast: true,

			// 成功后那张卡的文案。title 必填（卡片主行），description 选填（次行，只能是字符串）。
			success: { title: "任务已结案" },

			// 失败文案。不配就用核心兜底文案（含 reason），别指望它替你写业务语。
			failure: { title: "结案未完成" },

			// 卡片上的唯一按钮。id 指向 handlers 的键 —— 本页没这个键就不画。
			// 为什么只给一个：Toast 是 3 秒级提示，多按钮会被误点；要更多操作去列表里点。
			button: { id: "open-log", text: "看日志" },

			// 弹给谁：'all'（缺省）= 所有开着本插件的页面各弹一条；'origin' = 只有发起页弹。
			// 说明：'all' 是默认值，因为宿主本来就把终态推给每条连接，过滤是额外成本；
			// 只想"谁点的谁看见"时才改 'origin'（比对记录的 origin 字段，pool.ts:167）。
			scope: "all",

			// 是否额外走 BroadcastChannel。缺省 false，**任务通知不要打开**：
			// SSE 已经覆盖所有页面，再广播一次结果是每页弹两条。
			// 只有「不落记录的纯提示」或「非 SSE 消费者」才用，见本节末尾广播一节。
			broadcast: false,
		},

/* ───────── 3. host/executors/close-task.ts：执行器（Node 侧） ─────────
 * 这段跑在宿主进程，拿不到页面、也弹不了任何界面 —— 只能上报进度和结果，
 * 界面全部由页面订阅记录后自己画。所以这里一行 UI 代码都不该有。
 */
registerExecutor("close-task", async (args, ctx) => {   // 🆕 宿主级注册表，按 "<插件>:<短名>" 收口
	const { taskId, workspace, note } = args as {
		taskId: string;
		workspace: string;
		note?: string;
	};

	// 进度是"主动上报"，不是心跳：不报也能跑完（只是长任务看起来像卡住）。
	// 每次上报都会写进记录并由 SSE 推给所有页面，所以别在循环里每行都报，会打爆通道。
	ctx.progress(1, 4, "读取台账");
	const task = await runSkill(workspace, ["show", "--id", taskId, "--json"]);

	ctx.progress(2, 4, "核对在办列表");
	const listing = await runSkill(workspace, ["list", "--json"]);
	// 抛错即失败：核心捕获后把记录结算为 failed，并按 notify.failure 渲染。
	// 错误信息会进 reason，最终出现在兜底文案里 —— 写人话，别塞栈。
	if (!isOpen(listing, taskId)) throw new Error("任务已不在办");

	ctx.progress(3, 4, "写入结案记录");
	await runSkill(workspace, ["close", "--id", taskId, "--summary", note ?? "已完成"]);

	ctx.progress(4, 4, "提交台账");
	await gitCommitAndPush(workspace);

	// 返回值进 record.result；核心再把 taskId/workspace 合并进 detail，
	// 于是第 0 段按钮能从 detail 里取到重跑所需的参数（不需要额外传）。
	return { taskId, workspace };
});

	const { tasks } = useTasks({ project: TASK_PROJECT, groups: [JOB_GROUP] });

	return tasks.map((task) => {
		// 按钮跟着状态走：跑着的没什么可看，给"看会话"；结束了才给"看日志 / 重跑"。
		const ids = task.status === "running"
			? ["open-session"]
			: ["open-log", "retry"];

		// 画出来就是死按钮，用户点了以为坏了。

			.filter((id) => buttonHandlers[id] !== undefined)
			.map((id) => ({ id, onClick: () => buttonHandlers[id]?.(task) }));

		return <TaskRow key={task.id} title={task.title} detail={text} buttons={buttons} />;
```

#### 广播：默认关，别当主通知

**一、要不要广播？默认值是什么？**

| 场景 | 走什么 | 默认 |
|---|---|---|
| 任务终态通知（本方案主职） | 宿主记录 + SSE | **不广播**，`notify.broadcast = false` |
| 终态弹不弹卡片 | `notify.toast` | `true` |
| 弹给所有页面还是只发起页 | `notify.scope` | `'all'` |
| 不落记录的临时提示（"已复制"/"连接已恢复"） | `notify({ broadcast: true })` 或干脆本页 | 本页 |
| 跨 window / iframe / 非 SSE 消费者 | `BroadcastChannel` | 用的时候才开 |

为什么任务通知不该广播：宿主已经对**每条** SSE 连接各推一份终态（`host/task-center.ts:145-154`），
再加一条 `BroadcastChannel` 就是同一件事走两条线，每个页面收两遍 → 弹两条。**没有"要不要"的问题，是不需要。**

**二、广播要配哪些参数？**

| 参数 | 类型 | 默认值 | 含义 / 为什么 |
|---|---|---|---|
| `notify.broadcast` | `boolean` | `false` | 是否额外走 `BroadcastChannel`。开之前先问：SSE 为什么不够 |
| `notify.scope` | `'all' \| 'origin'` | `'all'` | 只影响"弹不弹"，不影响"记录有没有"；`'origin'` 靠 `record.origin`（`pool.ts:167`）判断是不是发起页 |
| `notify.toast` | `boolean` | `true` | `false` = 只存记录、不打扰（页面列表里仍可见） |
| `notify.success` / `failure` | `{ title, description? }` | 核心兜底 | 文案；`description` 只能是字符串（跨页要能克隆，`ui/feedback/notify.ts:99-102` 对非字符串直接抛） |
| `notify.button` | `{ id, text }` | 无 | `id` 必须是本页 `handlers` 的键；**广播路径禁止带按钮**（函数跨不了页，`toast-queue.ts:68-79` 类型上 `actions?: never`） |
| 通道名 | 由核心固定（`NOTIFY_CHANNEL`） | — | 任务通知不给配。改名 = 换协议，旧页面收不到（`runtime/notify.ts:21-23`） |
| `project` / `group` | `string` | 默认项目 / `'default'` | **这才是"发给谁"的开关**，不是广播开关 |

**三、广播发到哪？当前发起的插件实例，还是所有？**

分两层看，**都不存在"按插件实例"这种分区**：

| 层 | 谁收得到 | 收不到谁 |
|---|---|---|
| SSE（默认路径） | 所有连到**同一宿主**的页面：同窗口多标签、不同窗口、不同 workspace 都算 | 宿主没连上的页面；页面关了不做补投递 |
| `BroadcastChannel`（`broadcast: true`） | **同一 origin** 的所有 window / tab / iframe | 别的端口 / 域名；宿主进程（Node 没有这个 API，`runtime/notify.ts:171-182` 无该全局时返回 `null`） |

两个必须写进注释的事实：

1. **广播没有"只发给发起者"这回事**。`BroadcastChannel` 收不到自己 post 的消息，所以本页要靠
   "自己发出的消息回流"（`remote: false`）才弹一次 —— 一旦发出去，同源所有页面都会收到。
   想只让发起页看见，靠的是 `scope: 'origin'` 过滤，不是靠广播范围。
2. **N×N 风险只在页面侧发起时存在**：3 个页面各发一次 = 每页收 3 条 = 9 条。
   所以广播的规矩是「**只由发起页发一次，接收页只收不发**」；服务端抢占标记那一套不需要，
   因为服务端根本没有 `BroadcastChannel`（`runtime/notify.ts:165-182`）。

**四、本插件要不要用广播？** 不用。台账的面板 / Toast / 刷新全在 SSE 这条线上，
`notify.broadcast` 保持 `false`，等真有跨 iframe 的消费端再开。

## Conclusion

已定稿（十二条）：

1. 后台只存状态，**不发通知**；没有「后端发广播」这回事。
2. 页面订阅 SSE 长连接拿终态，**各自**渲染 Toast；开 3 个页面就各弹 1 条，不用抢、不用广播。
3. 调用时传 `notify` 配置（`toast` 开关、成功/失败文案、按钮 id、`scope`、`broadcast`），存进宿主记录；缺省值 `toast: true` / `scope: 'all'` / `broadcast: false`。
4. 按钮是本页函数，**本页没注册就不画**；别的页面天然不受影响。
5. 刷新后的可点性 = 记录还在 + 初始化代码重跑（重新注册 handlers），不存「已展示」标记。
6. 使用方只写两处：`mountTaskToasts`（一次，监听 + handlers）、`startTask`（每次，传 notify）。
7. **进度不用心跳**：执行器主动上报，核心只转发；三类执行体的进度统一成「行/百分比 + 日志尾部」。
8. 前端只订阅核心，不直连 agent 或脚本；会话与进程都属于宿主，页面只是观众。
9. 报不报进度由执行器决定：不报也能跑完、也能通知，代价只是长任务看起来像卡住。
10. 广播降级为可选通道：主通知走 SSE，`notify.broadcast` 缺省 `false`；广播只服务跨 window / iframe / 非 SSE 消费者，且启用时必须解决 N×N 重复（只由发起页发一次）。
11. 消费端最终只写 2 处必选（入口挂载 + 发起调用），执行器注册或脚本二选一，UI 展示可选。
12. 列表按钮与 Toast 按钮**无机制区别**：都是 `id + 参数 → handlers[id](task)` 同一段程序。后端只存状态，不存按钮、不存 token；页面按 `task.status` 决定画哪些按钮。

执行侧未定：只有 agent 会话一种执行体，通用后台任务（shell / 自定义执行器）尚无实现。
