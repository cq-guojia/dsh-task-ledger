## Background

用户 2026-11-25 提出：看板任务行的「释放 / 取消 / 删除」三个按钮是否应该像「直接结案」那样改成后台执行——它们的底层都是台账写命令，都要跑 git，可能比较慢；「继续」不管（它是起会话、不写台账）。

已核实的事实（读源码，不靠对话）：

1. **三个动作确实都是写命令、都涉及 git**：`packages/skill/src/internal/actions/registry.go:44-90` 的命令名册里，只有 `list`/`stats`/`owners`/`logout`/`show`/`history`/`validate` 标了 `ReadOnly: true`；`claim`、用于释放的 `set --release`、用于取消的 `close --cancel`、`delete` 都不是只读。非只读命令走 `packages/skill/src/internal/shell/runner.go:146-248` 的同一条事务路径：`stepf("check")` → `GuardBeforeWrite` → `stepf("sync")` → `SyncDown`（git 拉取）→ `stepf("write")` → 业务写 → `stepf("commit")` → `Commit` → `stepf("push")` → `Push`（git 推送）。`stepf` 只在宿主设 `TASK_LEDGER_STEPS=1` 时往 stderr 打 `#step <阶段>`（`runner.go:23-28`）。
2. **确实可能慢**：`packages/plugin/src/client/api.ts:314`（`TASK_WRITE_TIMEOUT_MS = 120_000`）与 `packages/plugin/src/host/repositories/task.repository.ts:15`（`WRITE_TIMEOUT_MS = 120_000`）都按最长两分钟设超时，说明 git 同步/推送耗时长是真实场景，不是臆测。
3. **仓里现在是两套机制并存**：`直接结案`与`交给Agent结案`已走核心后台任务中心（单一 `TaskRecord.progress` 源，弹窗/TaskBar 同源披露，核心 toast + onSettled 刷新）；而释放/取消/删除仍走 `postTaskAction` 的同步 NDJSON 流（`task-row.ts:153-161` cancel、`:182-190` delete、`:739-746` claim/release），前端自己 `busy` 锁按钮、自己 `onStep` 翻阶段文案（`:130-138`）、自己 `notify` + `refresh`。同类写动作两套披露、两套终态处理，分裂。
4. **目标形态**：按 `direct-close.service.ts` 的同一套模式把这三个动作也纳入后台作业——host 跑 skill 读真实 `#step` 五阶段，经唯一写入口 `jobs.reportProgress` 写 progress，弹窗/TaskBar 共读；提交即返回、同一任务同一时刻一个作业、终态由核心 toast + 顶层 onSettled 刷新。

## Process

### 已拍板（用户 2026-11-25）

- **key 每个动作独立**：`release:<任务号>` / `cancel:<任务号>` / `delete:<任务号>`；以后新增写动作照这个模式各给一个前缀，监听不同 key 即可，不为每个动作写特例。核心按 `(project, key)` 归一乐观行、宿主按 key 判重；动作独立 key 使不同动作可并行、同一动作同一任务不会双跑。
- **key 不是多余**：核心 `startTask` 必须有 key 才能把乐观行与服务端帧对上；「只认 close 前缀」是本仓 `board-home.ts:270` 自己写的过滤，核心 `onSettled` 对任何 key 都回调。放宽本仓判定即可支持新动作，核心不用改。

### 完整方案（三个动作一起改，共用一套实现）

**共通骨架**：把 `direct-close.service.ts` 的「claim → register → spawn skill 读 `#step` → reportProgress → settle」抽成**一个通用写命令后台执行体**（如 `write-job.service.ts`），结案与三个新动作都调用它，不复制第二份；`index.ts` 的 submit 回调按 `kind` 分派到同一个执行体，传进动作命令与文案。

| 动作 | key | 宿主命令 | 提交参数 | 终态文案 |
|---|---|---|---|---|
| 释放 | `release:<任务号>` | `set --release --id` | workspace、id、progressTexts | 已释放 / 释放失败 |
| 取消 | `cancel:<任务号>` | `close --cancel --id --summary` | workspace、id、summary（理由）、progressTexts | 已取消 / 取消失败 |
| 删除 | `delete:<任务号>` | `delete --id --summary` | workspace、id、summary（留言）、progressTexts | 已删除 / 删除失败 |

每个动作都带八段文案（起始 / check / sync / write / commit / push / 成功 / 失败）随 `args.progressTexts` 由客户端按界面语言透传，宿主不写中文。状态进度经唯一 `reportProgress` 写 `TaskRecord.progress`，弹窗 notice 与 TaskBar 共读。终态 `completionConfig` 按动作生成 `toast.success/failure.title.description`，不挂「查看会话」按钮（这些动作不开会话）。

**三个动作的具体改法**：

1. **释放**：`task-row.ts:739-746` 的 `postTaskAction({action:"release"})` 改为 `startTask({kind:"release", key:releaseJobKey(id), args:{workspace,id,progressTexts}})`；确认弹窗提交后即返回，行侧不自己 notify/refresh，也不设 `busy` 长锁——改由作业态驱动按钮禁用与看板刷新。命令仍是 `set --release`，skill 侧不动。
2. **取消**：`task-row.ts:153-161` 的 `cancelTask` 改为 `startTask({kind:"cancel", key:cancelJobKey(id), args:{workspace,id,summary:reason,progressTexts}})`；带理由的输入框保留，理由作为 `summary` 透传给 `close --cancel`。`cancelError` 不再承载命令失败（失败走作业终态），只留提交本身的错误（如网络 / 作业已存在）。
3. **删除**：`task-row.ts:182-190` 的 `deleteTask` 改为 `startTask({kind:"delete", key:deleteJobKey(id), args:{workspace,id,summary:note,progressTexts}})`；留言透传给 `delete --summary`。**历史页删除**（`history-list.ts:588-601`）是同一动作的第二个入口，一并改：key 用 `delete-hist:<src>:<line>`（或用 fingerprint 拼），args 带 `src`/`line`/`fingerprint`/`summary`，命令仍是 `delete --src --line --expect`；两处共用同一套文案与执行体。

**必须一起处理的边界**：

- **onSettled 过滤**：`board-home.ts:270` 的 `if (!key.startsWith("close:")) return` 改为「本仓 project 下的所有作业都刷新」（或按已知前缀集合），否则三个新动作终态不刷看板。
- **行按钮禁用**：`task-row.ts:479/529/545` 现在用 `busy || closing`，`closing` 只认 `close:<任务号>` 的作业；动作独立 key 后，要把「同一任务有任一后台作业在跑」纳入禁用条件，避免作业跑着还能再点释放/取消/删除。
- **失败呈现**：核心 toast 只显示 `title`，失败原因在 `TaskRecord.reason` 里、不弹给终端用户（`model.d.ts:37-43,107`）。行内 `cancelError`/`deleteError` 仍保留提交期错误；命令失败要有可见反馈（toast 失败标题 + 看板刷新后任务仍在办）。
- **并发**：动作独立 key 允许同一任务的不同动作并行，但 skill 的 `SyncLock` 是整命令级、按仓库串行（`cli.go:731`），所以真并行会排队等锁（最多 60s），不会写坏数据；UI 侧仍按上一条禁用同一任务的其它动作，避免用户连点造成队列。
- **认领（claim）**：同是写命令，用户本轮只点名三个按钮，**本任务不改**；`postTaskAction` 的 NDJSON 链路因此仍要保留给认领用，不删。
- **继续 / resume**：起会话不写台账，不改。

### 专家评审（2026-11-25，三组只读）

三组评审一致结论：**方向正确，通用写命令后台执行体是最小可靠形态**（客户端 setTimeout / 包一层 NDJSON 都做不到 SSE 基线恢复 + 核心 toast 载体，否决）。但按原方案直接开工有 4 个 BLOCKER 和一批遗漏，均已并入下方修订方案。

**BLOCKER（必须改）**：

1. **submit 入口只认 `close:` key**（`index.ts:186-188`）：`release/cancel/delete/delete-hist:` 全被 `throw "提交缺 close:<任务号> key"` 挡掉。改为按已知前缀集合解析，`kind` 用显式 switch（close-agent 仍走 session.service，其余走通用执行体），历史删除 key 单独解析 src/line，不共用 `taskId === ""` 判据。
2. **作业 store 写死「已结案」**（`session-job.store.ts:51,128-136`）：`CloseJobKind` 只有两种、`completionConfig` 后缀硬编码「（已结案）/（失败）」。改为 `JobKind` 含三类新 kind；`claim/register` 增加 `completionTexts:{success,failure}` 与 `category`，由客户端随 args 透传（否则会弹「任务结案丨XXX（已释放）」，分类语义错）；`rowButtons` 对新 kind 返回空。
3. **历史删除参数在 submit 无校验**：旧路由 `routes.ts:494-526` 校验 `history/` 前缀 + `.md` + 无 `..`、`line>0`、指纹 `^[0-9a-f]{12}$`。新 submit 必须一字不差复用（抽公共 parse/validate），否则错误从"提交期可见"退化为"后台跑完 git 才失败"。`actOnTask` 收 `id:""` 无正确性问题（`task.repository.ts:100-110` 有 history 时不传 `--id`），前提是 src/line/fingerprint 齐全。
4. **作业态没驱动弹窗/按钮，历史缓存漏清**：`busy` 在 `startTask` 返回即清零（`task-row.ts:395`），`ReasonTaskModal`/`CancelTaskModal` 无 `locked`（`cancel-task-modal.ts:65-94`）会立刻可关、进度无处看；`history-list.ts:611-616` 的 `monthCache.clear()`/`captureDeletion`/`props.onDeleted()` 绑在同步成功分支，后台终态的 `onSettled` 只 `refresh()` 不清这些（`board-home.ts:268-275,938-944`）。改为：弹窗加 `locked`/`onBackground`（仿 `close-task-modal.ts`），终态 effect 里做全部本地清理。

**CONCERN（开工前定取舍）**：

5. **并发 / 超时（用户 2026-11-25 追问后定案：只做 UI 禁用，不加服务端互斥）**：三种超时先分清——60s 是 skill 抢 git 锁的**等待上限**（`locks.go:49-59`，每 100ms 重试，等满报「另一个会话正在同步同一份台账…请稍后重试」）；30s 是单个 git 操作的超时（`gitops.go:26`）；120s 是宿主杀整条命令的硬超时（`runner.ts:120-127`、`task.repository.ts:15`）。60s **不是** HTTP 请求超时。
   - **同时结束两个任务 / 同一任务两个动作**：同一个台账内走同一把 git 锁，第二个等锁；等不到就 failed 并把 skill 的错误原文展示给用户「请稍后重试」。不同台账各拿各的锁，互不影响。这是 skill 既有行为，不是改造引入的，现在连点结案也一样。数据不会写坏（锁保住写序）。
   - **取舍**：不做服务端按 taskId 互斥（用户口径：等就等，超了弹清楚错误让他重试即可，不值得加一层）。只保留 UI 禁用防连点：同一任务有任一后台作业在跑时，该行释放/取消/删除/完成按钮变灰（`task-row.ts:479/507/529/545` 条件扩为扫描同 taskId 全部 key）。跨标签 / 刷新的并发交给 git 锁，失败由核心 toast 展示错误。
   - **失败要说清楚**：skill 的锁错误原文就是「另一个会话正在同步同一份台账（已等 60 秒），请稍后重试」，`settle` 已把它收进 `TaskRecord.reason`（`session-job.store.ts:255`）；终态 toast 的 description 要带上这句 reason（或至少「失败，请稍后重试」），不能只给个光秃秃的「失败」。
   - 历史行删除的互斥粒度是「那条历史行」（key 含 `src/line`，同 key 的 `claim` 已挡重复删同一行）；它不是在办任务对象，不与在办任务的作业互斥。
6. **重复提交静默吞掉**：`duplicate` 现返回既有 id（`direct-close.service.ts:78-82,102`、`index.ts:237-239`），用户点第二次"没反应"。新动作要在提交期给可见提示。
7. **超时**：`register` 缺省 `maxDurationMs=0` ⇒ reaper 空转（`session-job.store.ts:326,355,232-235`），现靠 runner 的 120s 兜底。新作业显式给 ≈130s。
8. **终态文案/i18n**：复用现有 `actionStep*` 五段，只新增每动作「起始/成功/失败」3 段 + 分类 `taskActionCategory`；`actionCancelDone`/`actionDeleteDone`/`actionReleaseDone` 从 `notify()` 移到 `completionTexts.success`，不能变死键；`STEP_LABEL`/`actionSyncing` 因 claim 与设置页仍同步而保留（`settings-page.ts:22,1259-1260`）。
9. **dispose 欠账（存量）**：`jobs.dispose()` 不杀子进程、不 settle running（`index.ts:140-148`、`runner.ts:109`），新动作放大；本轮至少 settle running，杀子进程可另评。
10. **`JOB_GROUP="session"` 命名债**：group 是任意字符串、无协议风险，可不改；若改须 `api.ts:493` 与 `session-job.store.ts:30` 两处同步。
11. **per-project notice watermark** 理论吞卡（多作业乱序回放时），概率低、成本大，本轮接受 id 去重为主。
