## Conclusion

四视角（架构 / 后端程序员 / 前端 / DSH 专家）独立评审一致结论（2026-11-21）：

- **是 bug，不是必须承受的代价。** 主因插件实现偏离核心库 `onGiveUp` 契约（`api.ts:95-99`）：核心把永久错误识别 + 有限退避做在 `stream.ts`，插件却无条件裸重连、丢弃 `reason.permanent`、`headers` 恒空。次因核心库缺陷：`retryDelaysMs` 未透传（`api.ts:249-256`，`TaskCenterHost` 无此字段），且把无限重连入口全下放给 `onGiveUp`，易写错。
- **触发码大概率不是 401，而是 404（或其它永久 4xx/3xx）。** 插件 `authorize` 恒 `"local"`（`index.ts:157`）自身不发 401；宿主无 server-wide 鉴权（`docs/dependencies/host-webserver.md`）；全仓无 `dsh-auth` 换票实现。401 只可能来自外层，或用户记忆的触发码未实测。真正进入零延迟循环的分支只有 `stream.ts:166`（永久错误）；`0/429/5xx` 走 1+2+4s 退避，用尽后同样经裸重连变无限循环，只是非零延迟。
- **触发条件**：SSE 请求持续拿到永久错误——路由未注册（webServer inject 未命中 → 404，见 `host/task-stream.ts:66-73`）、外层代理/重定向、或长断连耗尽退避。「改工作区名 / 后台操作」最多是制造一次流中断的契机；无证据表明它改路由地址（`client/api.ts:496` 与 `host/routes.ts:82` 同路径）。
- **循环性质**：非同一同步栈递归（`connectTaskStream` 的 async IIFE 在首个 `await doFetch` 让出），是微任务/promise 级紧循环；N 标签 = N 条循环打满 DSH 单进程事件循环与 socket，admin 同进程排队；关源头标签即恢复，符合单进程模型。浏览器侧（同域 6 连接上限 + 每轮基线投影重渲染）是「单标签卡死」次因。
- **方案评估**：(a)「换票刷 dsh-auth cookie」——本仓无此机制/接口，且真因非 401，不成立；(b) 传 `retryDelaysMs`——当前 API 不支持，且对永久分支无效；(c) 退避+上限——可行，计数器须放 `connectTasks` 闭包外；(d) 按 `reason.permanent` 停连 + 可见提示——对症，暂态错误仍走有界重连。成熟模式 = 指数退避 + jitter + 上限 + 熔断 + 按 reason 分流 + 跨标签 BroadcastChannel/Web Locks 选主；SharedWorker / Last-Event-ID 在本仓属过度设计（已有 `task-snapshot` 基线 + notice 去重）。
- **修复落点**：插件侧 `client/index.ts:214-227` 止血（必做，现 API 即可）；核心库补 `TaskCenterHost.retryDelaysMs` 透传 + 内建有界策略治本（可选增强，非最小修复）。卸载清理 timer + `disposed` 守卫必须做（`ctx.effect` :227）。
- **未决/需实测**：真机抓 `/api/task-ledger/task-center/stream` 的 Status 与重连频率；确认是否有外层 401 / 404 窗口。用户明确本轮不修。
