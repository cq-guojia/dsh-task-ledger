### 第四轮（2026-11-21，真机 A/B 对照 + Network 实证 —— 推翻以上所有静态结论）

**关键实测（不在案发现场的是失败请求，是长连接）**：
- 卡死时 Network：`stream` 只有 3 条、状态 **200**、持续 **5.4 分钟**；不是失败请求刷屏——失败请求在浏览器看不到（长连接建立后不刷新）。
- 卡死时 pending 的是宿主自己的 `session.phase`/`models`/`update-notifications`（Initiator 为 `client.js:4569`/`host-data.ts:121`），**没有一条 Initiator 指向本插件**。`rename` 本身 200/14ms 成功。

- **结论**：不是服务端被打满，是**浏览器到该域名的连接被本插件的长连接占满**，宿主自己的请求全部排队（Chrome 每域名 6 连接上限）。关标签释放连接即恢复，与症状完全吻合。

**确凿的代码缺陷（client/index.ts:214-227，源码与 dist 逐字一致）**：
1. **连接泄漏**：`:225` `connectTasks()` 建立连接 A、`:226` `connectTaskLayout(ctx)` 内部又调一次 `connectTaskCenter`（core `api.ts:275-278`），后者 `streamConn?.close()` 关掉 A 后另建 B；B 的 disposer **被丢弃**（`connectTaskLayout` 返回 void）。`:227` cleanup 只持有 A 的 disposer，**关不掉活的 B**。每次 apply/重连都可能留一条关不掉的长连接。
2. **无界重连**：`:220-222` `onGiveUp` 裸重连、忽略 `reason.permanent`、无退避无上限。401/404 下无限重连（core `stream.ts` 永久错误零延迟 giveUp）。
3. 二者叠加：多标签 × 反复重连 → 每条标签泄漏多条 SSE 长连接 → 占满浏览器每域名 6 连接 → 全站请求排队转圈。

**修复方向（用户尚未授权动手，本轮只定性）**：止血在插件侧——接住 `connectTaskLayout` 的 disposer（或改为不重复接线）、cleanup 关全部连接、`onGiveUp` 按 `reason.permanent` 分流 + 有界退避；治本在核心库——`connectTaskLayout` 应返回 disposer、`retryDelaysMs` 透传、内建闸门。改完必须 rebuild dist/client.js 才生效。

### 第十轮（2026-11-21，用户要求专家组 + 社区调研：SSE 该不该用、为什么出这种问题）

**真机验证**：断掉插件 SSE 后用户反馈「一切正常」——连接数假说**确证**。

**社区实践（web 搜索，server-sent-events.com / wikantik / javascriptroom 等）**：
- HTTP/1.1 每域 6 连接上限是浏览器硬约束；多标签各开 EventSource 会耗尽池，后续所有请求(API/图片)无限 stall——**与本症状逐字吻合**。
- 成熟做法：① 跨标签共享一条 SSE（BroadcastChannel/Web Locks/SharedWorker）；② 迁移 HTTP/2 让多路复用消除连接上限；③ 服务端 `retry:` + 客户端 jitter 防重连风暴。
- **重要纠正**：WebSocket 同样占 TCP 连接、同样受每域 6 连接上限，"换 WS"不解决本问题；它价值在单连接承载双向逻辑流。

**架构专家组裁决**：
1. **SSE 技术无辜，是用法问题**——该用 SSE（本机单用户/后台状态推送正合适），错的是"每窗口无条件常驻一条"的连接策略。
2. **为什么出这问题**：通用陷阱（多标签 + h1.1 6 连接）被 DSH 插件模型放大——CJS 闭包无跨标签共享、多标签共享 origin、宿主 follow + 各插件连接共用一个池彼此不可见、每窗口 apply 无条件开连；单标签调试完全不可见，只在多标签叠加时爆发。
3. **正式修复路线**：消费端 Web Locks 选主 + BroadcastChannel 广播把插件 SSE 从 N 条降为全标签 1 条（唯一解症状路径）；核心库 `connectTaskLayout` 返 disposer / retryDelaysMs 透传 / 内建单飞+闸门（治本于全平台）。**核心的单飞只是单标签内单例，解决不了跨标签连接数**，不能等核心再修本插件。SharedWorker / WebSocket / 单独升 h2 均不取。

## Conclusion

四视角（架构 / 后端程序员 / 前端 / DSH 专家）独立评审一致结论（2026-11-21）：

- **是 bug，不是必须承受的代价。** 主因插件实现偏离核心库 `onGiveUp` 契约（`api.ts:95-99`）：核心把永久错误识别 + 有限退避做在 `stream.ts`，插件却无条件裸重连、丢弃 `reason.permanent`、`headers` 恒空。次因核心库缺陷：`retryDelaysMs` 未透传（`api.ts:249-256`，`TaskCenterHost` 无此字段），且把无限重连入口全下放给 `onGiveUp`，易写错。
- **触发码大概率不是 401，而是 404（或其它永久 4xx/3xx）。** 插件 `authorize` 恒 `"local"`（`index.ts:157`）自身不发 401；宿主无 server-wide 鉴权（`docs/dependencies/host-webserver.md`）；全仓无 `dsh-auth` 换票实现。401 只可能来自外层，或用户记忆的触发码未实测。真正进入零延迟循环的分支只有 `stream.ts:166`（永久错误）；`0/429/5xx` 走 1+2+4s 退避，用尽后同样经裸重连变无限循环，只是非零延迟。
- **触发条件**：SSE 请求持续拿到永久错误——路由未注册（webServer inject 未命中 → 404，见 `host/task-stream.ts:66-73`）、外层代理/重定向、或长断连耗尽退避。「改工作区名 / 后台操作」最多是制造一次流中断的契机；无证据表明它改路由地址（`client/api.ts:496` 与 `host/routes.ts:82` 同路径）。
- **循环性质**：非同一同步栈递归（`connectTaskStream` 的 async IIFE 在首个 `await doFetch` 让出），是微任务/promise 级紧循环；N 标签 = N 条循环打满 DSH 单进程事件循环与 socket，admin 同进程排队；关源头标签即恢复，符合单进程模型。浏览器侧（同域 6 连接上限 + 每轮基线投影重渲染）是「单标签卡死」次因。
- **方案评估**：(a)「换票刷 dsh-auth cookie」——本仓无此机制/接口，且真因非 401，不成立；(b) 传 `retryDelaysMs`——当前 API 不支持，且对永久分支无效；(c) 退避+上限——可行，计数器须放 `connectTasks` 闭包外；(d) 按 `reason.permanent` 停连 + 可见提示——对症，暂态错误仍走有界重连。成熟模式 = 指数退避 + jitter + 上限 + 熔断 + 按 reason 分流 + 跨标签 BroadcastChannel/Web Locks 选主；SharedWorker / Last-Event-ID 在本仓属过度设计（已有 `task-snapshot` 基线 + notice 去重）。
- **修复落点（第二轮修正）**：核心库做基础闸门是**治本必需**（按用户既定原则 `17-0231:19`），不是可选增强；插件侧 `client/index.ts:214-227` 按契约正确接线是止血，两者都要做。核心闸门细节见第二轮「责任边界裁决」。卸载清理 timer + `disposed`/epoch 守卫必须做。
- **未决/需实测**：真机抓 `/api/task-ledger/task-center/stream` 的 Status 与重连频率，并同时看 `board/snapshot`——解开「同回调为何只有 SSE 坏」的矛盾，决定是路由未注册 / dispose 断流 / apply 重入 throw / 紧循环自维持。401 是否真实触发仍未实测。用户明确本轮不修。
