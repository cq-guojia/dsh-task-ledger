**「正常占用」为什么触发（三层分开，勿混）**：
1. 错误来源 = 集成层。client `index.ts:225` apply 即无条件连 SSE；服务端 `serveTaskStream` 与插件数据面都在 `ctx.inject(['webServer'])` 未命中时静默放弃注册（core `host/task-stream.ts:66-73` 注释自认「apply 时 webServer 常未 active」；插件 `index.ts:112-122` warn+return），路由缺席 ⇒ 404。
2. 放大器 = 插件接线。`client/index.ts:220-222` 裸重连 + core `stream.ts:44-46,164-166` 永久错误零退避 ⇒ 微任务级紧循环；N 标签打满 DSH 单进程。
3. 契约误导 = 核心 API。`onGiveUp` 注释只讲 401 可刷新（`api.ts:95-99`），但 403/404 同桶；`retryDelaysMs` 未透传（`api.ts:222-263`）；永久错误默认静默、应用必须自己读 `reason.permanent`。「改工作区名/后台操作」不是根因，最多是一次流中断契机。
4. **原始错误钉死（第三轮 very thorough 排除法，2026-11-21）**：状态码是 **404，且只能是 404**。排除链：插件 `authorize` 恒 `"local"` ⇒ 401 分支（`task-stream.ts:84,92`）不可达；403 只在 submit（`task-submit.ts:49`）不在 stream；无代理/base/SW ⇒ 无 3xx；stream handler 不校验 method/参数 ⇒ 无 400/405；source 故障回 503（可重试）。唯一剩下的永久状态 = 宿主对未注册 path 回 404。`registerRoutes` 的 13 条 path 与 `/task-center/stream` 全不撞（`routes.ts:246-635`），冷启动无重复注册 throw。
   机制：SSE 路由走**独立 inject fiber**（`task-stream.ts:70-77`）而非 JSON 路由那个回调（`index.ts:112`）；cordis 语义是「依赖就绪才回调」（`core/docs/dependencies/dsh-host.md:211-215`，`ctx.inject` = `plugin({inject,apply})`），所以**不是永久放弃，是启动时存在注册窗口**——client `apply` 在 `:225` 无条件立刻连，请求可早于该 fiber 把路由挂上 ⇒ 首连 404。
   自维持：404 被判永久 ⇒ 零退避裸重连 ⇒ 紧循环打满单进程事件循环 ⇒ 本该完成注册的 inject fiber 排不上队 ⇒ 持续 404。关标签去掉循环，fiber 才跑完、路由才挂上、恢复。**这解释了「网络正常、压力不高也触发」——不是环境问题，是启动/生命周期时序 + 放大器自锁。**

## Conclusion

四视角（架构 / 后端程序员 / 前端 / DSH 专家）独立评审一致结论（2026-11-21）：

- **是 bug，不是必须承受的代价。** 主因插件实现偏离核心库 `onGiveUp` 契约（`api.ts:95-99`）：核心把永久错误识别 + 有限退避做在 `stream.ts`，插件却无条件裸重连、丢弃 `reason.permanent`、`headers` 恒空。次因核心库缺陷：`retryDelaysMs` 未透传（`api.ts:249-256`，`TaskCenterHost` 无此字段），且把无限重连入口全下放给 `onGiveUp`，易写错。
- **触发码大概率不是 401，而是 404（或其它永久 4xx/3xx）。** 插件 `authorize` 恒 `"local"`（`index.ts:157`）自身不发 401；宿主无 server-wide 鉴权（`docs/dependencies/host-webserver.md`）；全仓无 `dsh-auth` 换票实现。401 只可能来自外层，或用户记忆的触发码未实测。真正进入零延迟循环的分支只有 `stream.ts:166`（永久错误）；`0/429/5xx` 走 1+2+4s 退避，用尽后同样经裸重连变无限循环，只是非零延迟。
- **触发条件**：SSE 请求持续拿到永久错误——路由未注册（webServer inject 未命中 → 404，见 `host/task-stream.ts:66-73`）、外层代理/重定向、或长断连耗尽退避。「改工作区名 / 后台操作」最多是制造一次流中断的契机；无证据表明它改路由地址（`client/api.ts:496` 与 `host/routes.ts:82` 同路径）。
- **循环性质**：非同一同步栈递归（`connectTaskStream` 的 async IIFE 在首个 `await doFetch` 让出），是微任务/promise 级紧循环；N 标签 = N 条循环打满 DSH 单进程事件循环与 socket，admin 同进程排队；关源头标签即恢复，符合单进程模型。浏览器侧（同域 6 连接上限 + 每轮基线投影重渲染）是「单标签卡死」次因。
- **方案评估**：(a)「换票刷 dsh-auth cookie」——本仓无此机制/接口，且真因非 401，不成立；(b) 传 `retryDelaysMs`——当前 API 不支持，且对永久分支无效；(c) 退避+上限——可行，计数器须放 `connectTasks` 闭包外；(d) 按 `reason.permanent` 停连 + 可见提示——对症，暂态错误仍走有界重连。成熟模式 = 指数退避 + jitter + 上限 + 熔断 + 按 reason 分流 + 跨标签 BroadcastChannel/Web Locks 选主；SharedWorker / Last-Event-ID 在本仓属过度设计（已有 `task-snapshot` 基线 + notice 去重）。
- **修复落点（第二轮修正）**：核心库做基础闸门是**治本必需**（按用户既定原则 `17-0231:19`），不是可选增强；插件侧 `client/index.ts:214-227` 按契约正确接线是止血，两者都要做。核心闸门细节见第二轮「责任边界裁决」。卸载清理 timer + `disposed`/epoch 守卫必须做。
- **未决/需实测**：真机抓 `/api/task-ledger/task-center/stream` 的 Status 与重连频率，并同时看 `board/snapshot`——解开「同回调为何只有 SSE 坏」的矛盾，决定是路由未注册 / dispose 断流 / apply 重入 throw / 紧循环自维持。401 是否真实触发仍未实测。用户明确本轮不修。
